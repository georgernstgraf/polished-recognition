# Pitfalls

Things that do not work, subtle bugs, and non-obvious constraints.
Read this file carefully before making changes in affected areas.

- RecognitionService cannot be annotated with @AndroidEntryPoint (Hilt). Manual DI via Application class is required.
- `GET /v1/models` is not universally supported. GROQ returns it, some local models (Ollama/LM Studio) may not. Always handle 404 by falling back to free-text model input.
- The `AudioRecord` thread must run at `THREAD_PRIORITY_URGENT_AUDIO` to avoid buffer underruns on slower devices.
- `callback.results()` must be called from the same thread that received `onStopListening()` — use `runOnUiThread` or Main dispatcher.
- WAV header requires little-endian byte ordering. Standard `DataOutputStream.writeInt()` is big-endian and will produce corrupt WAV files.
- Retrofit instances for dynamic base URLs must be cached. Creating a new Retrofit instance per call leaks OkHttp connection pools.
- `SpeechRecognizer.RESULTS_RECOGNITION` expects `ArrayList<String>` — plain `List<String>` causes a ClassCastException in Bundle.
- `settings.gradle.kts` must use `dependencyResolutionManagement` (not `dependencyResolution`) for Gradle 8.x.
- `runCatching { }` is not a coroutine scope — suspend functions cannot be called inside it. Use `withContext(Dispatchers.IO)` instead.
- `RecognitionService.Callback.readyForSpeech()` requires a `Bundle` parameter (pass `Bundle.EMPTY`) in API 30+.
- The STT `response_format=verbose_json` returns both `text` and `language` fields in one call — prefer it over separate calls for language detection.
- Kotlin 1.9.x compiler cannot read Kotlin 2.1.x stdlib metadata. When test dependencies pull newer Kotlin stdlib transitively, upgrade the project Kotlin plugin to match.
- `PromptStore` must initialize `gson` before `defaults`. Kotlin initializes properties in declaration order. A `loadDefaults()` call that references `gson` after its declaration hits an uninitialized property → NPE → swallowed by catch → fallback defaults used silently.
- `SttProviderConfig` and `LlmProviderConfig` data classes have 5 constructor params with `id` as the only default. In Kotlin 2.1.x, positional args with default params at the front require named args for the rest.
- The `ChatResponse` constructor takes `List<ChatChoice>`, not `List<ChatMessage>`. Each `ChatChoice` wraps a `ChatMessage`.
- `captureNullable<ChatRequest>()` requires an explicit type parameter in the slot approach. Prefer `slot<ChatRequest>()` for capture semantics.
- `TextInputLayout.error` persists indefinitely until explicitly set to `null`. If no `TextWatcher` clears it on text change, the red error state remains even after the user corrects the input. Always pair `textField.addTextChangedListener { layout.error = null }` when setting `layout.error` from validation logic.
- R8 full mode strips generic type information from the `Continuation<? super Response<T>>` parameter in Kotlin suspend functions within Retrofit interfaces. `HttpServiceMethod.parseAnnotations` casts to `ParameterizedType` and crashes with `ClassCastException: java.lang.Class cannot be cast to java.lang.reflect.ParameterizedType`. Use non-suspend `Call<T>` return types in code paths that run on `Dispatchers.IO` to avoid the `Continuation` type resolution entirely.
- AGP 8.2.2 bundles R8 that cannot parse Kotlin 2.1.x metadata. The R8 warning "An error occurred when parsing kotlin metadata" appears on every release build. Minimum AGP version for Kotlin 2.1 is 8.6, minimum R8 is 8.6.17. Upgrade AGP to 8.7+.
- Kotlin 2.1.x makes `javaClass.classLoader` return type `ClassLoader?` (nullable). Calling `.getResource()` without `?.` produces a compilation warning. Use `javaClass.classLoader?.getResource(…)`.
- `ResponseBody.create(MediaType?, String)` is deprecated in OkHttp 4.12.0, but the replacement extension `String.toResponseBody(MediaType?)` does not exist in this version. Suppress the warning with `@Suppress("DEPRECATION")` rather than using the unavailable extension.
- OpenRouter's `/v1/models` endpoint is unauthenticated — returns model list for any token (even garbage). The validate flow shows a green checkmark for an invalid token. Always follow model fetch with a minimal chat API call that checks for 401/403 before confirming the token works.
- `ChatRequest` had no `maxTokens` field. The token test call needs `max_tokens=1` to minimize cost. Added as optional `maxTokens: Int? = null` with `@SerializedName("max_tokens")` — existing callers are unaffected since the field defaults to null (omitted from JSON).
- R8 full mode inlines private methods and reorders instructions within `onCreate()`. `lateinit var` view fields initialized via `findViewById` in a separate `bindViews()` method may be accessed in `loadSettings()` BEFORE `bindViews()` assignments execute. Use `val by lazy { findViewById(...) }` instead of `lateinit var` + separate init method.
- `isShrinkResources = true` removes views from layouts in release builds even when the view is referenced in Java/Kotlin code via `findViewById`. Keep `isShrinkResources = false` unless resource keep rules are explicitly verified.
- `android.R.drawable.ic_media_stop` does not exist in the Android SDK. Create a custom `VectorDrawable` for a stop/square icon.
- OxygenOS (OnePlus) overrides system drawable icons — `ic_menu_preferences` renders as a wrench, not a gear. Use custom drawables for guaranteed appearance across OEMs.
- Model save validation must reject empty model text when the model list is non-empty. The check `model.isNotEmpty() && model !in models` short-circuits on empty, allowing blank model names to be saved, silently overwriting valid STT/LLM config.
- `ArrayAdapter.clear()` and `addAll()` modify the internal `mOriginalValues` list (not `mObjects`) when `mOriginalValues` is non-null — which it always is after constructor initialization. A custom `Filter.publishResults()` that calls `clear()` + `addAll()` never updates the displayed data (`mObjects`), only corrupts `mOriginalValues`. Use `BaseAdapter` + `Filterable` with a directly owned display list. Never use `clear()`/`addAll()` in a custom ArrayAdapter filter.
- `ArrayAdapter.setNotifyOnChange(false)` is never reset to `true` after a filter's `publishResults` returns, leaving the adapter in a permanently non-notifying state that causes crashes on subsequent text input.
- AutoCompleteTextView dropdown items (`DropDownListView`) cannot contain focusable child views (e.g. `ImageButton` with `focusable="true"`). The ListView refuses to deliver `onItemClick` for any row that has a focusable child — even tapping the non-focusable text area of that row fails. Keep dropdown items as plain `TextView` or use views with `focusable="false"`. For secondary actions, move controls outside the dropdown (separate dialog, long-press, etc.).
- To use an `AutoCompleteTextView` as a tap-to-open selector (HTML `<select>` behavior): set `inputType="none"`, `threshold = Int.MAX_VALUE`, `cursorVisible="false"`, and — critically — `setOnClickListener { showDropDown() }`. Without the click→`showDropDown()` hook the dropdown never opens, because `inputType="none"` blocks typing and the popup is otherwise only triggered by text input reaching `threshold`. Also set `focusable="false"` + `focusableInTouchMode="false"` (keep `clickable="true"`): `EditText` defaults to focusable-in-touch-mode, so the **first** tap on an unfocused field is consumed to gain focus and does not fire `onClick` — the symptom is needing 2–3 taps to open the dropdown until the field has been used once. Re-create the adapter (`setAdapter(ArrayAdapter(...))`) rather than `clear()`/`addAll()` when the option list can change between foregroundings (e.g. via `onResume` after a Settings detour), so the displayed list is always authoritative regardless of ArrayAdapter internal `mOriginalValues` state. Guard programmatic `checkBox.isChecked =` restores with a silence-flag so the `OnClickListener`/`OnCheckedChangeListener` doesn't write the just-read value back to prefs.
- Device rotation destroys and recreates the Activity by default. If a recording Activity uses `AudioRecord`, `onDestroy()` → `audioRecorder.cancel()` discards the PCM buffer. Always add `android:configChanges="orientation|screenSize"` to the `<activity>` element in the manifest for any Activity that handles recording.
- Release builds sign with `signingConfigs.release` which reads `app/release.keystore` (local copy of `~/.android/debug.keystore`). CI decodes `RELEASE_KEYSTORE` secret (same keystore) into `app/release.keystore`. Both use the same key — no signature mismatch.
- `installRelease` disappears as a Gradle task when the `release` build type has no `signingConfig` set. Restore it with a **conditional** signingConfig (see below) or pass `-Pandroid.injected.signing.*` properties per-invocation.
- A conditional `signingConfig` is required to satisfy F-Droid/build CI AND local `installRelease` simultaneously. Define it in `app/build.gradle.kts` guarded by `if (file("release.keystore").exists())`, both when creating `signingConfigs.release` and when assigning `release.signingConfig`. The keystore is gitignored, so it exists only on the dev machine (→ signed → `installRelease` works, APK named `app-release.apk`) and is absent in build.yml, release.yml, and F-Droid's build env (→ unsigned → `app-release-unsigned.apk`, matching `build.yml`'s `fail_on_unmatched_files` path and `fdroid/*.yml`'s `output:`). An **unconditional** `signingConfigs` block breaks F-Droid because the referenced keystore file is missing in their container. release.yml is unaffected because it signs the AAB via `-Pandroid.injected.signing.*`, which is orthogonal to build.gradle.
- `versionCode` must be a positive integer. The awk formula `printf "%d%02d%02d00"` produces `0` for `v0.0.0` because `0000000` parses as `0`. Use `01` suffix instead of `00` (`printf "%d%02d%02d01"`) to guarantee a positive result.
- AGP 9.x drops the `org.jetbrains.kotlin.android` plugin — it is no longer required and must be removed from `plugins` blocks. The `kotlinOptions {}` configuration block is also unavailable in AGP 9.x; JVM target is derived from `compileOptions { targetCompatibility }`.
- The `r0adkll/upload-google-play` GitHub Action returns a generic "Precondition check failed" error with no details when Play Console blocks a commit. Use the direct Play Developer API (via `scripts/query-play-console.py` style calls) instead to get precise error messages.
- Android VectorDrawable (`<vector>`) does not support SVG `<filter>`, `<pattern>`, `<clipPath>`, or `<feDropShadow>` elements. Gradients, drop shadows, mesh patterns, and glow effects from a high-quality SVG cannot be directly ported — render to PNG instead.
- Local `./gradlew assembleRelease` signs with the debug keystore (`app/release.keystore`, SHA1: `EE:C4:BF:...`). CI `release.yml` signs with the upload keystore (SHA1: `E2:34:27:...`). These are different keys. Play Console rejects AABs signed with the wrong key. Always use the `release.yml` workflow (triggered by `v*` tags) for Play Store uploads, not locally built AABs.
- Whisper models (especially v3) hallucinate phrases like "Thank you." or "Thanks for watching." after trailing silence. The default system prompt (#49) instructs the LLM to strip only the trailing hallucination (empty string only if the entire transcription is one) — "Subtitles by Amara" never appears on Whisper. On-device, a **stored** system prompt override keeps the old default until Settings → restore default.
- The global `UncaughtExceptionHandler` in `PolishedRecognitionApp` launches `CrashDialogActivity` in a separate `:crash` process via `Intent.FLAG_ACTIVITY_NEW_TASK`. If the crash occurs on the main thread during Activity lifecycle (e.g. `onCreate`), the intent may not be delivered before the system kills the process. The `:crash` process isolation is a best-effort mitigation — the dialog may not always appear for crashes during early app startup.
- F-Droid `AutoUpdateMode: VersionTag` is NOT a valid value. Valid values: `None`, `Version`, `VersionCode`.
- F-Droid `UpdateCheckData` must have exactly 4 pipe-separated parts. Extra pipes cause `ValueError: too many values to unpack (expected 4)` in `fdroid lint`.
- Backslashes in F-Droid `UpdateCheckData` regex (`\d`, `\s`) must be preserved. Using `sed` for replacement eats the backslashes. Use Python or heredoc instead.
- `fdroid lint` passes but `fdroid rewritemeta` and `fdroid build` may fail on unrelated apps in the same MR branch. This happens when the fork has additional metadata changes (e.g. a second app). Remove all files except the target app's metadata from the branch.
- fdroid/fdroiddata upstream master does NOT contain `at.priv.graf.zazentimer.yml` (MR !39945 is not yet merged). Including it in a polished-recognition MR branch causes the maintainer to reject with "Add only one app in one MR."
- `build.yml` cleanup step used `gh release list` without filtering, deleting ALL releases (including `v*` Play Store releases) when >7 total releases existed. Add `| grep '^build-'` to the pipeline.
- `release.yml` may not trigger when a `v*` tag is pushed in the same push as a branch commit. Push tags separately or delete and re-create the remote tag to re-trigger.
- `translate.ts` dispatch functions had `app_name: "ZazenTimer"` hardcoded — a copy-paste artifact from the original fork. Change to the correct app name.
- `getSettledStrings()` callers in `voting_api.tsx` pass only one argument (langId). The function now has a second optional parameter `threshold`. Backward compatible but callers should be updated to pass an explicit threshold.
- The `language_proficiencies` table uses `modelId` as its foreign key field (not `llm_modelsId`). Querying `prisma.language_proficiencies.findMany({ where: { llm_modelsId: ... } })` is a runtime error — the field doesn't exist in the Prisma schema. Use `modelId` and access via `p.modelId` (no `include: { llm_model: true }` needed).
- The `/strings/:sid` "Settlement Score" column in `voting_api.tsx` must sort and display `score` (proficiency-weighted sum), not `voteCount` (raw model count). The `getStringSettlement` return object provides both fields — using `voteCount` for the sort labeled "score" produces incorrect ordering and confuses users.
- F-Droid metadata: when `subdir:` is set, `output:` MUST be removed. fdroidserver's gradle APK auto-detection searches `root_dir/build/outputs/apk/release/` (root_dir = build_dir/subdir), so with `subdir: app` it finds `app/build/outputs/apk/release/*.apk`. Keeping `output: app/build/...` with `subdir: app` globs `app/app/build/...` (double `app`) → "Failed to find any output apks". For a single-module app (gradle root at repo root, module `app/`), the canonical block is `subdir: app` + `gradle: [yes]` + no `output:`.
- F-Droid metadata: with `subdir: app` set, `UpdateCheckData` is unnecessary — fdroidserver's default `UpdateCheckMode: Tags` check reads `app/build.gradle.kts` (relative to subdir) for versionCode/versionName. Removing it is correct (maintainer-requested); verified via `fdroid checkupdates` detecting the version.
- fdroidserver 2.4.5 (latest on PyPI) local-build toolchain gaps: (1) `~/.config/fdroid/config.py` is **deprecated/ignored** — use `config.yml` or env vars (e.g. export `ANDROID_HOME`, since default `sdk_path` is `$ANDROID_HOME`). (2) The bundled `gradlew-fdroid` (fdroidserver's trusted-gradle launcher, which REMOVES the project's `gradlew` + `gradle-wrapper.jar` and reads the version from `gradle-wrapper.properties`) has a SHA256 hash table that **predates Gradle 9.x** → "No hash for gradle version 9.5.1". The pip package doesn't even install the script; `common.py` default `gradle = FDROID_PATH/'gradlew-fdroid'` points to a missing file. Workaround for local verification: drop the real `gradlew-fdroid` (from the sdist tarball) into site-packages and replace its body with `exec <cached-gradle>/bin/gradle "$@"` (the build subprocess env does NOT reliably propagate `GRADLE_VERSION_DIR`/`JAVA_HOME`, so hardcode paths). These are fdroidserver-version issues, not metadata issues — F-Droid's production CI is unaffected.
- The app compiles with **JDK 21** (`sourceCompatibility/targetCompatibility = JavaVersion.VERSION_21`), despite AGENTS.md saying "Java 17 target". A local `fdroid build` must run with `JAVA_HOME` = JDK 21 or `compileReleaseJavaWithJavac` fails with `invalid source release: 21`.
- F-Droid **reproducible builds** require removing non-determinism from the release APK bytes. Two AGP-9 gotchas hit zazentimer: (a) a `BUILD_HOST` BuildConfig field fed by `hostname -s` — inherently machine-specific, so the GitHub Actions APK never byte-matches F-Droid's buildserver build. Drop such fields (or make them deterministic) before attempting reproducibility. (b) AGP embeds a **"Dependency metadata" APK signing block (ID `0x504B4453`)** that F-Droid's scanner rejects as CRITICAL ("found extra signing block 'Dependency metadata'" → `check apk` job fails). Disable it with `android { dependenciesInfo { includeInApk = false } }` (leave `includeInBundle` default so the Play AAB is unaffected). Verify locally with the fdroidserver scanner: `common.get_androguard_APK(apk).parse_v2_v3_signature()` then check `b.id for b in _v2_blocks` — should NOT contain `0x504B4453`.
- F-Droid `Binaries:` (top-level) must be formatted as a **2-line value with a trailing space** after the colon to satisfy CI's `fdroid rewritemeta`:
  ```
  Binaries: <trailing space>
    https://example.com/v%v/app.apk
  ```
  Local fdroidserver 2.4.5 rewrites this to a single line (version skew); do NOT run local `rewritemeta` after setting it — trust the CI canonical form. `AllowedAPKSigningKeys:` = lowercase hex SHA-256 of the signing cert (from `apksigner verify --print-certs`, or `keytool -printcert -jarfile` on the AAB — same key).
- Reproducible verification: with `Binaries:` set, `fdroid build <appid>:<vercode>` downloads the reference APK, verifies its signature against `AllowedAPKSigningKeys`, strips the signature, and compares to its own from-source build — look for "compared built binary to supplied reference binary successfully". The reference APK must be built with the SAME source transformation F-Droid applies (e.g. if metadata has a `prebuild` that strips a manifest line, the published APK must be built with that same strip), and with full git history (`fetch-depth: 0`) so any embedded commit-count matches.
- Non-release tags pollute `UpdateCheckMode: Tags` (zazentimer had `tested-2026-06-24` tags with the same versionCode as `v3.2.0` but newer date, so `checkupdates` picked the wrong commit and the job failed as "dirty"). Fix: `UpdateCheckMode: Tags ^v` to filter to version tags only.
- **R8 + reproducible builds:** `isMinifyEnabled = true` (R8) does NOT block F-Droid reproducibility on AGP 9.1.1. F-Droid's docs note R8's old CPU-core nondeterminism was fixed in R8 8.6.33/8.7.20/8.8+; AGP 9.1.1's bundled R8 is far past that, and `isShrinkResources = false` avoids the resource-shrinker nondeterminism. Verified: polished-recognition's R8 build "compared built binary to supplied reference binary successfully" across GitHub↔F-Droid. Only flag if the `fdroid build` byte-comparison actually fails, then diff the APKs (F-Droid "HOWTO: diff & fix APKs for Reproducible Builds").
- **Release signing key (polished-recognition):** moved OFF the debug keystore to a proper RSA-2048/~100y key (CN=polished-recognition, cert `62f9d7b0…a76a85`). `app/build.gradle.kts` signingConfig now reads a **gitignored `keystore.properties`** (rootProject) or `RELEASE_*` env vars (CI) — the old `android`/`androiddebugkey` defaults are GONE (no silent debug signing). `*.keystore` and `keystore.properties` are gitignored. To rebuild locally from a fresh clone: restore `app/release.keystore` + `keystore.properties` from the pass wallet, or set the `RELEASE_*` env vars. The new key is the **F-Droid** signing identity (`AllowedAPKSigningKeys`) — unrelated to the Play **upload** keystore (release.yml), so Play is unaffected. Signature change ⇒ uninstall any old debug-signed `installRelease` build once.
- **Key wallet (pass/GPG/SVN):** signing keys live in a `pass` store at `~/svn/georg/private/password-store` (GPG key `EC23CFDFDDA530BD`, SVN-synced, **not git**). Set `PASSWORD_STORE_DIR` (exported from `~/.bashrc`). Layout: `android/<app>/{keystore.b64, store-password, key-password, alias, cert-sha256, github-secret-names}` + `gitlab/schurlix-fork`. Retrieve the keystore: `pass show android/<app>/keystore.b64 | base64 -d > app/release.keystore`; passwords via the sibling entries.
- **F-Droid testers on headless emulators see no app network traffic** (no API key configured) and may incorrectly conclude "on-device ML claim holds." The app requires a user-configured STT/LLM API key to make any network call. The `INTERNET` permission is legitimate — for user-configured OpenAI-compatible endpoints, not analytics/tracking. When a reviewer questions network traffic, confirm it is emulator system traffic (Google connectivity checks) and clarify the cloud API architecture. (See MR !40029, pando85 test report.)
- `Settings.Secure.putString("voice_recognition_service", …)` from a non-system app throws `SecurityException` on OEM ROMs (Samsung One UI, Realme UI, ColorOS, MIUI) — `WRITE_SECURE_SETTINGS` is `signature|privileged`. This was the broken path behind removing the bound `RecognitionService`. The replacement is the auxiliary IME (`Settings.ACTION_INPUT_METHOD_SETTINGS`), which needs no privileged permission. (MR !40029, @bhavyashah04122005.)
- `InputMethodService` cannot request runtime permissions directly (it's a service, no activity result API). Use a transparent trampoline `Activity` (`MicrophonePermissionActivity`) that calls `registerForActivityResult(RequestPermission())` and `finish()`es; the IME launches it with `FLAG_ACTIVITY_NEW_TASK` when `RECORD_AUDIO` is missing.
- An auxiliary voice IME subtype needs `android:imeSubtypeMode="voice"` + `android:isAuxiliary="true"` in `res/xml/voice_method.xml`. `android:overridesIme` is **not a public attribute** — AAPT rejects it; omit it. A `<subtype>` requires a unique `android:subtypeId` (a hex int **within signed-int range**, i.e. < `0x80000000`; larger values fail resource linking).
- Recording audio inside an active `InputMethodService` on Android 14+ requires a foreground service of type `microphone`: declare `android:foregroundServiceType="microphone"` on the IME `<service>` and call `ServiceCompat.startForeground(this, id, n, ServiceInfo.FOREGROUND_SERVICE_TYPE_MICROPHONE)` only **after** `RECORD_AUDIO` is granted (else `startForeground` throws). `ServiceCompat` handles the version-branching of the 3-arg `startForeground`.
- IME input-view layouts must avoid `MaterialButton`/Material-components views: the `InputMethodService` inflates with the service context, whose theme is not a Material3 theme → `MaterialButton` crashes at inflation. Use plain `android.widget.Button` (e.g. `@android:style/Widget.DeviceDefault.Button.Borderless`) + `TextView`.
- `commitText` from a coroutine callback must hop to the Main thread; the `VoiceSessionController` already delivers events on Main (Handler(mainLooper)), so the IME's `handleEvent` can call `currentInputConnection.commitText(...)` directly.
- **IME layout: `?attr/` (Material theme attrs) crash in the service context** — concrete instance: `<ImageButton android:background="?attr/selectableItemBackgroundBorderless">` → `InflateException` → `UnsupportedOperationException: Failed to resolve attribute at index 13` → crash loop (system restarts the IME → `onCreateInputView` crashes again → the `UncaughtExceptionHandler` fires `CrashDialogActivity` repeatedly). Fix: `android:background="@null"` or `?android:attr/selectableItemBackgroundBorderless` (PLATFORM attr, resolves in any context). This generalizes the prior pitfall: **every** background/tint/style attribute in an IME layout must be a platform attr (`?android:attr/...`), a resource (`@color/...`, `@drawable/...`), or `@null` — never a bare `?attr/` (Material/AppCompat). Test IME layouts by switching the active keyboard to Polished; a crash here loops and the only recovery is `adb uninstall`.
- **Oplus (OnePlus/OPPO/Realme) ROM blocks adb secure-settings + IME ops from the shell** — `adb shell ime list/enable/set`, `adb shell settings put/delete secure ...`, and `adb shell pm grant ...` all throw `SecurityException: uid 2000 does not have WRITE_SECURE_SETTINGS` (or `GRANT_RUNTIME_PERMISSIONS`). Even `ime list -a` (read) is blocked. Everything (enable IME, set default keyboard, grant mic) must be done via the Settings UI. `dumpsys input_method` / `dumpsys package` (reads) still work and are how you verify IME registration (`mId=.../PolishedVoiceInputIME`, `mShowInInputMethodPicker=true`).
- **HeliBoard's mic button uses the system `voice_recognition_service` (bound `RecognitionService`), NOT the auxiliary voice IME.** Confirmed via the XDA HeliBoard+whisperIME tutorial (it `adb settings put secure voice_recognition_service ...`). So removing `PolishedRecognitionService` (#43) broke HeliBoard's mic→Polished integration. The auxiliary IME is invoked by (a) a keyboard with a dedicated voice-typing selector (Fossify — proven by @bhavyashah04122005), or (b) switching the active keyboard to Polished via the nav-bar switcher. AnySoftKeyboard similarly invokes the auxiliary IME (not the `RECOGNIZE_SPEECH` intent) when Polished is enabled. If HeliBoard's mic→Polished is wanted, the bound `RecognitionService` must be re-added (additive) — tracked as a possible follow-up.
- **`Spinner` dropdown items are unreadable in the IME service context** — platform `simple_spinner_item`/`simple_spinner_dropdown_item` inherit text color from the theme; the service context's default theme yields dark-gray text on a dark popup → near-zero contrast on Oplus. (Issue #44.)
- **`adb install -r` over a signature mismatch fails** with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`. The installed build's signing key must match the new APK. polished-recognition switched from the debug keystore to an RSA-2048 release key (2026-06-28); a phone with an older debug-signed build requires `adb uninstall` first (wipes Groq config) before `adb install`. Same-key reinstalls (`-r`) preserve the config.
- **GitLab PAT in a remote URL / credential.helper is exposed** — the token was embedded both in `origin`'s URL and as a `credential.helper` shell function (`!f() { echo "password=glpat-…"; }; f`) in the local repo `.git/config`. Both are plaintext on disk and (in this session) printed by `git remote -v`. Rotate via the GitLab web UI (`/-/user_settings/personal_access_tokens?scopes=api,write_repository`), strip the remote (`git remote set-url origin https://gitlab.com/…/<repo>.git`), `git config --global credential.helper store`, then a no-op `git push` (public fork's `git fetch` won't prompt — read is anonymous) to cache the new token. Verify with `GET /personal_access_tokens/self` (the `api` scope alone covers both `git push` and MR API; `write_repository` is redundant under it).
- **An auxiliary-only IME (`android:isAuxiliary="true"` on the only `<subtype>` in `voice_method.xml`) cannot be set as the primary keyboard — the nav-bar keyboard switcher isn't rendered when only one non-auxiliary IME is enabled.** Fix (#46, shipped `f4ebca4`): add a second, **non-auxiliary** keyboard `<subtype>` (`isAuxiliary` omitted → default false; `imeSubtypeMode="keyboard"`; unique `subtypeId` hex < `0x80000000`) to the same `<input-method>` so Polished appears as a selectable primary keyboard AND the switcher renders for `Gboard + Polished`. `isAuxiliary` is per-subtype, so one IME exposes both: the non-aux keyboard subtype (primary, selectable) + the existing aux voice subtype (HeliBoard/Fossify integration). Confirmed on-device: switcher renders for `Gboard + Polished` with the #46 build. **Do NOT add `android:isAsciiCapable="true"` to the non-aux keyboard subtype** — see the next pitfall for why.
- **AOSP "Manage Keyboards" greyed-out rule (`InputMethodSettingValuesWrapper.isAlwaysCheckedIme()`, `frameworks/base/packages/SettingsLib/.../InputMethodSettingValuesWrapper.java` + `InputMethodAndSubtypeUtil.isValidNonAuxAsciiCapableIme()`): an IME's enable/disable toggle is greyed out (disabled) only when EITHER (A) it's the sole enabled IME left (`getEnabledInputMethodList().size() <= 1`, no `isSystem`/ASCII requirement), OR (B) it's the last enabled **system** (platform-signed) + non-auxiliary + ASCII-capable **keyboard** IME. The current/default IME (`Settings.Secure.DEFAULT_INPUT_METHOD`) is **never** consulted in the greyed-out decision — AOSP explicitly allows disabling the current default (`InputMethodAndSubtypeUtilCompat` save path clears `DEFAULT_INPUT_METHOD` and lets `InputMethodManagerService` pick a new one). `isAuxiliary` only *excludes* an IME from counting toward `enabledValidNonAuxAsciiCapableImeCount` (via `if (imi.isAuxiliaryIme()) return false`); it never locks an IME. `isAsciiCapable()` returns true only if the subtype declares `android:isAsciiCapable="true"` — default is false. LineageOS's copy is byte-identical to AOSP `main`; no OEM override was needed to explain the observed behavior.**
- **`isAsciiCapable` decision (#46): deliberately NOT set on Polished's non-aux keyboard subtype.** On-device 7-row evidence table (Oplus/OnePlus, all consistent with AOSP — no OEM override):

  | State | Greyed-out | AOSP prediction | Match |
  |---|---|---|---|
  | Gboard alone | Gboard | (A) sole IME → greyed | ✓ |
  | Polished alone | Polished | (A) sole IME → greyed | ✓ |
  | HeliBoard alone | HeliBoard | (A) sole IME → greyed | ✓ |
  | OpenBoard alone | OpenBoard | (A) sole IME → greyed | ✓ |
  | Gboard + Polished | Gboard | count=1 (Polished not ASCII-capable) → Gboard last system non-aux ASCII kb → greyed | ✓ |
  | HeliBoard + Polished | neither | count=1 (Polished not ASCII-capable) → HeliBoard non-system → not greyed | ✓ |
  | Gboard + HeliBoard + Polished | none | count=2 (Gboard+HeliBoard) → none is last system | ✓ |

  Adding `isAsciiCapable="true"` would make Polished count → `Gboard + Polished` count=2 → Gboard not greyed → both toggleable → user could disable Gboard and strand Polished as the sole IME. Since Polished has **no QWERTY layout** (it's a voice bar), stranding would leave the user with no way to type normal text. Leaving `isAsciiCapable` unset keeps AOSP's user-protection (Gboard stays greyed in `Gboard + Polished`, preventing the strand). The switcher still renders regardless (confirmed on-device) — `isAsciiCapable` affects only the greyed-out toggle rule, not switcher rendering. Trade-off accepted: Polished is "second-class" in `Gboard + Polished` (Gboard protected) vs `Gboard + HeliBoard` (neither protected, since HeliBoard declares `isAsciiCapable` and is a real typing keyboard).- **Under `Theme.DeviceDefault` (non-Material), bare `?attr/` (AppCompat/Material theme attrs) and `?attr/textAppearance*` do NOT resolve** — AAPT/aapt2 accepts them at build time (no error), but inflation throws `UnsupportedOperationException: Failed to resolve attribute at index N` at runtime. This generalizes PITFALL #83 (IME service context) to *any* non-Material theme: use `?android:attr/...` (platform), `@android:style/...`, `@color/...`/`@drawable/...`, or explicit `android:textSize`/`android:textColor` literals. Concrete instance in #45: `item_manage_language.xml` had `?attr/selectableItemBackground` and `?attr/textAppearanceBody1` → both replaced with `?android:attr/selectableItemBackground` and `textSize=16sp`+`?android:attr/textColorPrimary`. The platform `?android:attr/textColorPrimary`/`secondary`/`tertiary` ARE DayNight-aware (the `values-night` resource set overrides them), so explicit `textSize` + platform text-color attrs preserves dark mode without Material.
- **A bare `AutoCompleteTextView` with `inputType="none"` (HTML `<select>` behavior) needs a manual `setOnClickListener { showDropDown() }` + `threshold = Int.MAX_VALUE`** — Material's `ExposedDropdownMenu` end-icon provides the tap→open hook automatically; a plain `AutoCompleteTextView` does not, and `inputType=none` blocks typing so the dropdown is otherwise unreachable. Already documented for the IME (PITFALL #37) but it also applies to the post-#45 Settings provider/target-language dropdowns, which lost Material's exposed-dropdown wrapper. Keep `focusable="false"`+`cursorVisible="false"`+`clickable="true"` so the first tap opens the dropdown (not just focuses the field).
