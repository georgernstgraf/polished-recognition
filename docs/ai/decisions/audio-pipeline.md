## 2026-11-20: #123 — Loop-Guard läuft NUR hinter einem erzwungenen Bruch, kollabiert statt zu kürzen

Die Seam-Study (#122) nennt Whisper-Repetition-Loops als dominante Fehlerquelle
— das gilt für den **Study-Korpus** (Musik, bandbegrenztes Telefon), nicht für
den Alltag: eine Seam unterschreitet `qualityMin` in ~6 % der Fälle, zwei in
Serie ~0,4 %, drei ~0,02 %. Der Guard wird deshalb nicht als Policy-Maschine
gebaut.

- **Gate:** `fragment.seamForced` — unter dem Produktionsdefault
  `FORCED_ONLY` bekommt der Decoder Pre-roll + Prompt genau dort, also ist der
  harte Schnitt die einzige Stelle, an der ein Loop entsteht UND über den
  Prompt ins nächste Fragment wandert. Stille-aligned Cuts laden bare und
  erreichen den Guard nie.
- **Aktion:** `LoopGuard.collapse()` (auf `LoopMask.loopSpans`, Defaults 4× /
  ≤8 Tokens) ersetzt jeden Loop-Span durch seine **erste Periode** —
  Groß-/Kleinschreibung und Satzzeichen dieser Periode bleiben. Kollaps statt
  Truncation: ein Tail-Loop hinterlässt genau eine Wiederholung und nichts
  Halluziniertes dahinter, ein Loop mitten im Text behält den echten Text
  danach. Eine Untergrenze für „legitime Wiederholung" ist nicht nötig — der
  gefährliche Normalfall ist per Gate ausgeschlossen.
- **Ort:** vor dem Store in `FragmentTranscriber` (`transcripts[index] = …`),
  damit `promptTail()` und `snapshot()` den gekürzten Text sehen.
- **Kein** Setting, **kein** eigener Evidenz-Stream: `session.json` stellt
  `sttRaw` (Serverantwort) gegen `sttTrimmed` (gespeichert), daneben steht
  `seamForced`.

## 2026-11-12: #124 — the geometry is "slice + search window %", and the stage line tells the truth



- **Trigger (measured, 380 retained sessions / 787 real requests from the daily driver):** the shipped rule `search = max(2 s, S)` with the cut in the window's LATE half produced fragments of **1.5–2 × the nominal size** — body median 17.7 s at the nominal 10-s floor, max 37 s. Three consequences: (a) the Settings value lied about the fragment length; (b) the auto-sizer's fit treated `S` as the real duration → systematic ~1.75× undershoot → permanently clamped at the 10-s floor; (c) 61 % of dictations never committed a live fragment (the first window closes at 2S = 20 s).
- **The new geometry (owner decision):** a **slice** is a fragment's MAXIMUM length and its boundary is arbitrary; the **search window** is the last `p` % of the slice and the only region a cut may land in. So `cut ∈ [sliceEnd − window, sliceEnd]` and `fragment ∈ [Slice·(1−p), Slice]`. `SearchSpan` (LATE_HALF / FULL_WINDOW) is **deleted** — the percentage replaces it. **Equivalence proof for migration:** the old production behaviour (S = 10, search = S, late half) IS slice 20 s with p = 25 %, so the rename changes numbers, not behaviour. The Settings migration doubles the legacy `fragment_seconds_override` for the same reason.
- **Auto-sizer, stepwise REMOVED (owner decision):** no ±50 % anchor, no `lastAppliedSeconds`, no write-back — `sliceSeconds()` is a pure read, so the grey value in Settings is by construction the applied value. No profile-version bump: Gson ignores the dropped field, the ~800 existing samples survive (the version guard exists only for POISONED profiles).
- **Budget fixed at 2.0 s in code (owner decision, no UI).** 2.0 s reproduces the measured status quo on gregor (median stop→raw 1.98 s) and lets GROQ use very large slices (137 s). The search is "the largest slice whose predicted `stop→raw` fits", via the measured cost model `encode(Tail) + (encode+t)²/(2·L̄) + a + b·Tail` (Theil–Sen fit `a`/`b` from the profile; `L̄ = Slice(1−p/2)`; the tail uniform in `[0, Slice]`). Measured: `a` = 0.55 s (GROQ) / 0.76 s (gregor), `b` = 1.95 %/s / 2.57 %/s.
- **The LOCAL ENCODE is the hidden third cost:** measured from `prepare.json`, OGG costs **7.9 % of the audio length** (1.31 s for a 16.5-s fragment), WAV **0.1 %**. It runs on the preparer thread BEFORE the request, so it lengthens the in-flight window the user taps into — that, not the network, is why gregor/ogg punishes large slices. The rate now lives in the profile (`encodeMsTotal`/`encodeAudioMsTotal`, fed by the new `onFragmentEncoded` hook) so the search can price it.
- **Internal quality floor `Slice ≥ 8 s/(1−p)`, and it WINS over the budget** (`chooseSlice`). Owner decision: the Settings fields stay 5–180 s / 10–60 % with no cross-validation — "who wants to shoot their own foot may do it" — but the auto-sizer must never produce a degenerate slice. At the 2.0-s budget the floor never binds in practice (gregor/ogg 20 s, gregor/wav 67 s, GROQ 137 s).
- **Search-window auto (new):** it cannot be derived from latency — the signal is the **forced-cut rate** (a searched cut that found no candidate). Rule: `> 2 %` forced → +5 %, `< 0.5 %` → −5 %, else unchanged; bounds 10–60 %, bootstrap 30 %. The window is measured since the LAST step (`seamsTotalAtStep`/`seamsForcedAtStep`) so resolving the value twice cannot double-step. Fed by the new `onSeamCut(forced)` hook (searched cuts only — the stop-tap tail is not a cut).
- **Stage line (#116, same session):** the number is the **audio length of the fragment currently being transcribed**, emitted at request start — never the backlog. Measured: the backlog was median 10.7 s / p90 22.0 s while the real stop→raw wait was median 1.65 s (RTF 0.07); the user read it as a countdown. The emit-at-tap is gone (the line honestly shows "Compressing…" until the first request leaves).
- **Analyzer:** `--slice-seconds` / `--search-percent` replace `--fragment-seconds` / `--search-seconds` / `--search-span`. The run default shifts (21 s slice + 30 % = 14.7–21 s vs the old 21–23 s), so the #129 baseline must be re-run; published runs stay valid as "model v1".
- **Seam statistics: a low stitch rate is the design WORKING, not a too-low gate (owner correction, same day).** 537 measured seams on real dictations: 2 % forced, 4 % stitched, Q median 131 / p10 21. That means 98 % of cuts found a real silence and 96 % of those pauses are deep enough that the pre-roll/prompt/trim net is not needed — and bare seams are the CHEAP ones. Stitching them all would buy nothing and cost audio, context and trim risk. Consequence for #129: these seams cannot decide `qualityMin`; the knob only discriminates where seams are SICK, so the natural-find premise stands and the corpus sweep brackets the value. Do not re-derive "the gate is too low" from a low stitch rate.
- **Test strategy:** the core/controller test adapters keep the pre-#124 parameters and translate them EXACTLY (`slice = F + W`, `window = W/2` — the old late-half span IS the new window), so all 28 existing preparer expectations keep their meaning; the new semantics get their own tests (`chooseSlice`, the floor, the encode-rate effect, the adaptive %).

## 2026-10-15: #148 — per-request STT timing in the bundle: the SUCCESSFUL attempt's wall-clock only
- **Fields:** `FragmentRecord.sttSentAt` / `sttReceivedAt` (epoch ms wall-clock bracketing the whole `SttRequestRunner.run` call — its internal retry loop included, i.e. the request duration as the app saw it) + `uploadBytes` (the composed upload's size, so the bundle stays self-contained once `uploads/` ages out under retention eviction).
- **Minimal shape (per the issue):** the failure branch records `uploadBytes` + `sttError` but NO timing — the RTF metric only makes sense for successes; per-retry timestamps are explicitly deferred ("retry counts optional later").
- **The 400-retry path (prompt fallback) resets BOTH timestamps** before the prompt-less attempt — the failed attempt's latency never contaminates the successful one's record.
- **`uploadBytes` is captured at COMPOSITION time**, not in the outcome fold: the composed `upload_%06d.*` is deleted in the finally-block BEFORE the fold runs, and `File.length()` on a deleted file returns 0.
- **Analyzer:** `FragmentDto` mirrors all three fields (the round-trip drift guard enforces it); `BundleIo.requestMs` / `realTimeFactor` helpers; `report` gains `reqs` / `req(s)` (mean) / `RTF` (mean) / `up(kB)` columns plus a slowest-request / worst-RTF summary line; legacy bundles parse (nullable defaults) and simply contribute no timed request.

## 2026-10-13: #135/#136 — capture PCM spools to DISK; session RAM becomes O(1) (A03 OOM crash fixed at the root)
- **Crash (A03, release + #133/#134, 2026-10-13 23:32, owner-supplied `trc.txt`):** `OutOfMemoryError: Failed to allocate a 46438416 byte allocation` in `AudioRecorder.copyPcmRange` → `ByteArrayOutputStream.toByteArray` → `Arrays.copyOf`, on the live fragment-worker thread (`FragmentPreparer.startWorker$lambda$6`) — uncaught → process death mid-dictation, no snapshot, dictation lost. Arithmetic: 46,438,416 B ≈ 1451 s ≈ a ~24-min dictation; at that length the BAOS internal array (≤2× after growth doubling ≈ 64 MB) plus the per-fragment full-buffer copy blew the A03's 128-MB heap growth limit. The OnePlus would hit the same wall around 40+ min.
- **Root cause:** `AudioRecorder.copyPcmRange(start, end)` — the `PcmSource` access EVERY fragment encode/search-span/pre-roll uses — called `bufferStream.toByteArray()`, copying the WHOLE session buffer to slice a small range ("one full copy per fragment is cheap against a 7-s encode cadence" — written when sessions were short). Same full-copy pattern in `stopPreservingBuffer` (toByteArray + WavWriter.write = TWO full copies at stop) and `snapshotPcm`.
- **Stage 1 (`c5f2046`, #135):** in-RAM block chain (`ArrayDeque<ByteArray>`, 512-KiB blocks) — `copyPcmRange` copies only the requested range; growth allocates one block at a time (no contiguous double-allocation); `WavWriter.writeHeader` extracted so the stop WAV assembles with ONE full copy instead of two. Shipped and green before the owner redirected.
- **Stage 2 (`2c362db`, #136, owner directive "after a fragment comes back, the buffer gets free again"):** the consumer inventory showed the full-session RAM buffer has almost NO consumers left — shadow + full-context assemble from the FRAGMENT FILES (`assembleChunks`), uploads are the fragment files, the legacy batch path is reached only for EMPTY recordings, retention has a `retainFile` API. So the recorder went FILE-BACKED: capture appends 16-kHz mono PCM to `cacheDir/recording.pcm` (one `RandomAccessFile`, one lock); `copyPcmRange` = seek+read; `PcmSource` contract unchanged → `FragmentPreparer` untouched. `stopSessionWavFile(): File` streams header + spool (64-KiB copy buffer); `snapshotToFile` = disk copy; `restoreFromFile` RENAMES the process-death snapshot onto the spool (even a restored session never materializes in RAM). The controller threads the FILE through `runTranscription`/`prepareAudioFiles`/`retainAudioEvidence` (`retainFile`); the legacy `WavChunker` branch materializes bytes only when reached (44-byte empty recordings).
- **Result:** session RAM is O(1) — a 60-min dictation costs the same few-MB window a 2-min one did; the A03's 128-MB heap no longer bounds dictation length. Evidence fidelity unchanged (`session.wav` = original PCM streamed from the spool — no OGG round-trip). Disk: cacheDir grows by spool + stop WAV for the session's lifetime (evictable); capture writes 32 KB/s to flash.
- **Watch:** `snapshotPcm`/`restorePcm` remain as byte-based compat APIs (tests only). The on-device long-dictation check on the A03 is pending (owner). PAUSED parking keeps the spool on disk — the parked-audio semantics survived the refactor.

## 2026-08-31: Optional Ogg/Opus compression before STT upload (#60)
- **Choice**: Opt-in `compress_audio` setting transcodes the recording to Ogg/Opus (24 kbps) via the **platform MediaCodec encoder + MediaMuxer `MUXER_OUTPUT_OGG`** before upload; light pure-Kotlin PCM conditioning (80 Hz high-pass + peak normalization) runs before encoding. - **Considered**: Community ffmpeg-kit forks (`ffmpegkit-maintained` group-ID swap, `com.mrljdx`), self-built minimal FFmpeg via NDK (F-Droid-friendly but a large NDK toolchain to maintain), AAC/m4a via MediaCodec (accepted too, but Ogg/Opus is the better-supported speech codec at low bitrates).
