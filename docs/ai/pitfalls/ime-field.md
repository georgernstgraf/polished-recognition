# Pitfalls — IME and the Target Field

Moved out of `PITFALLS.md` in #206; entries are verbatim. New pitfalls in this area are appended here.

- **Das `InputMethodService`-Default geht in Landscape FULLSCREEN — der Extract-Editor mit „Done" deckt die App und wirkt im Dark-Theme hell (2026-11-25, #210, Gerätebefund OnePlus 7T).** Ohne eigenes Override liefert `onEvaluateFullscreenMode()` in Landscape true: die Plattform versteckt das Zielfeld und zeigt ihren eigenen Extract-Text-Editor (OxygenOS rendert ihn auch in Dark Mode hell/weiß). Der Owner meldete das als „weißes Raw-Feld im Landscape" und als „edit field with a stupid Done button" — zwei Symptome, eine Ursache, und kein Code von uns hatte sie je erzeugt (das Default war seit IME-Existenz aktiv, nur nie im Landscape benutzt). Fix: `onEvaluateFullscreenMode() = false` in `PolishedVoiceInputIME` (unconditional — das IME ist eine Leiste über dem Zielfeld in jeder Orientierung), gepinnt durch `ImeFullscreenModeTest` für beide Orientierungen. Regel für jede künftige IME-Arbeit hier: jede ererbte `onEvaluate*`-Plattform-Default ist ein Verdächtiger, wenn sich Verhalten **nur in einer Orientierung** ändert.

- **Die Fensterprobe muss so groß sein wie der Text, den sie verifiziert — ein konstantes Fenster friert die Live-Vorschau nach dem ersten Fragment ein (2026-11-25, #205, Gerätebefund OnePlus 7T).** Der Reconciliation-Probe las konstant 64 Zeichen vor dem Cursor. Echte Fragmente sind 500+ Zeichen: ab dem zweiten Fragment zeigt das Fenster nicht mehr `B + Anfang unseres Texts`, sondern nur das **Ende der Komposition** — beide exakten Vergleiche scheitern, `decide` bricht ab (`abort tick reason=window`), und das Display ist für den Rest der Session tot, bis Send den polierten Text liefert (`outcome=CLEARED`, die Composition wird vorher abgeräumt). Deterministisch in JEDER Session; der Verdacht „Satzzeichen/Leerzeichen am Fragmentende" war ein Fehlgriff (die Fragment-Texte sind stabil, `markers=0`). Regel: die Probe-Länge wird aus dem erwarteten Inhalt dimensioniert (`LivePreviewReconcile.windowLength` = B + K + sent; Bind/Terminal: B + P), und `decide`/`classify` lokalisieren die B-Grenze tolerant — Kontext **links** von B darf im Fenster stehen (ein längerer Request zieht nur Prä-Kontext hinein), **rechts** von B darf nur ein Präfix von P stehen. Diagnose-Ausbau: die Abort-Zeilen tragen `window=<len> tail=<24 Zeichen>`; genau dieser Befund war ohne die Signatur nicht aus den Logs zu lesen.
- **`setComposingText` ERSETZT die Composing-Region — „nochmal alles senden" verdoppelt committeten Text (2026-11-25, #205).** Die Live-Vorschau resendet das ganze Zwischentext-P an jedem Tick; das ist nur korrekt, solange die Region noch UNSERE Composition ist (`setComposingText(P)` ersetzt sie). Hat der Client sie beim Feldende committet (`onFinishInput` → `finishComposingText`, der AOSP-Default), ist die Region leer und dasselbe `setComposingText(P)` fügt P ein ZWEITES Mal ein. Deshalb: (a) beim Bind gegen die Fensterprobe **nie** Text senden, den das Feld schon zeigt — `B + P` heißt dort „K = P committet", und nur das Delta (`P − K`) wird komponiert; (b) auf der lebenden Verbindung ist `B + K + sent` die Erwartung, und `sent` muss mitgeschrieben werden, weil ohne es ein Delta-Compose die alte Region überschreibt und den sichtbaren Text LÖSCHT; (c) die Fensterprobe kann Composition und committeten Text nicht unterscheiden — jede „Reparatur", die das annimmt, ist eine Duplikat- oder Verlustroute. Der Terminal-Schritt klassifiziert deshalb **nach** dem Abbrechen der Composition (`setComposingText("")`), nie davor.
- **B muss um die Selektion gekürzt werden, sonst passt der Selection-Restore nie (2026-11-25, #205).** Der erste `setComposingText` ersetzt die markierte Auswahl. Wird B als reines `getTextBeforeCursor(64)` gemerkt, enthält es den markierten Text, der danach aus dem Feld verschwunden ist — der Guard `Fenster == B` kann nach dem Löschen der Composition nicht mehr wahr werden, und der Snapshot landet immer nur im Clipboard. Regel: B = Fenster minus `selection.text`, wenn das Fenster damit endet.
- **Ein Display-Callback aus `FragmentTranscriber` darf nie zur Fragment-Failure werden (2026-11-25, #205).** `notifyDisplay()` läuft im seriellen Worker; ein werfender Listener liefe in den `catch (Throwable)` des Worker-Loops und würde das Fragment als STT-Fehler verbuchen, obwohl die Transkription gelungen ist. Der Callback wird deshalb gefangen + `CoreLog.w`, und der Zustand wird VOR dem Event aktualisiert, damit eine neue IME-Instanz ihn synchron lesen kann (Events werden nicht wiederholt, `emit` verwirft ohne Zuhörer).

- **`showSoftInput` from `onResume` does nothing on the OnePlus; the window is not focused yet (2026-11-19, #173).** Measured on the OPO (`f6de166c`, OxygenOS 12): `am start` on the Workbench showed no keyboard at all and `dumpsys input_method` read `mShowRequested=false mInputShown=false` although the code had posted `showSoftInput` from `onResume`. The identical call from `onWindowFocusChanged(hasFocus = true)` works first try (`mShowRequested=true mInputShown=true`, screenshot `/tmp/opencode/wb-173b.png`). Fix pattern in `WorkbenchActivity.revealSoftKeyboard()`: keep the `onResume` attempt, retry once the window holds focus, and also call `WindowCompat.getInsetsController(window, field).show(ime())` — both paths are idempotent while the IME is already up. Do not "fix" this with a delay constant; the trigger is window focus, not time.

- **The IME window is edge-to-edge from Android 15 — up to API 34 the platform inset the IME CONTENT itself (2026-11-13, #157).** Two emulator runs with the SAME build and 3-button navigation settle it: API 31 (Android 12) IME window frame `[0,1932][1080,2400]` with the content ending above the nav bar `[0,2274][1080,2400]` (the platform applied the inset), API 35 (Android 15) IME window `[0,2058][1080,2400]` with the content reaching the display bottom — the bottom control row was drawn UNDER the nav bar buttons. The layout had no inset handling at all, which was correct until API 34 and wrong from 35. Consequences: (a) a bug report "keyboard under the nav bar" is NOT testable on the owner's opo (Android 12) — a month of daily 3-button use proves nothing either way, the enforcement starts at API 35 with `targetSdk ≥ 35`; (b) the fix (`service/ImeWindowInsets` + a `ViewCompat.setOnApplyWindowInsetsListener` on `ime_root`) needs **no** SDK gate: on API 31 the view never receives a dispatch (the platform consumes the inset at the decor, verified — no `insets` line in `ime-lifecycle.log`), so padding it there would only double-pad if the insets arrived, which they do not; (c) always rebuild the padding from the XML base value, never from `root.padding*`, because insets are dispatched repeatedly (show, rebind, rotation) and the padding would grow; (d) merge navigation bar and cutout per side with `max`, not a sum — in landscape the 3-button bar sits inside the cutout area. Debug hook: the IME writes a deduplicated `insets sdk=… nav=l/r/b cutout=l/r/b base=… applied=…` line into `files/logs/ime-lifecycle.log` on every change.
- **Never take a theme colour as an `Int` — `TypedValue.data` is a RESOURCE ID whenever the attribute resolves to a reference (2026-11-13, #160).** `theme.resolveAttribute(attr, value, true)` yields an ARGB literal only for literal values; `Theme.DeviceDefault` does that on AOSP, so the bug is invisible on an emulator. An OEM night skin (OxygenOS/ColorOS) points `textColorPrimary`/`textColorTertiary` at `@color` **selectors**, so `value.data` is a framework resource id (`0x01xxxxxx`) and `setTextColor(int)` reads its high byte as ALPHA — `0x01` = 0.4 % opacity = invisible, in every state. Use `context.themeColorStateList(attr)` (`ui/ThemeColors.kt`, `obtainStyledAttributes(...).getColorStateList(0)`); it also keeps the enabled/disabled states. Symptom that exposed it: the "Advanced" slice/search fields were unreadable in system dark mode on the OnePlus while fine in light mode. Two follow-on traps: (a) a themed colour resolved as a `ColorStateList` still needs the RIGHT state — `isEnabled = false` stacks the selector's disabled alpha on the tertiary colour and drops contrast from 5.4:1 to 2.1:1, so a read-only display should take the enabled variant explicitly; (b) a naive contrast test cannot catch this class, because it resolves the same literal theme values on the host — the test must launch the screen under a **selector-based** theme (`Theme.Material` / `Theme.Material.Light` do exactly that), see `ThemeColorResolutionTest` (#161 generalises this into a full audit).

- **`?android:attr/windowBackground` can be a DRAWABLE, not a colour (2026-11-14, #161).** Resolving it as a `ColorStateList` (`obtainStyledAttributes(...).getColorStateList(0)`) throws `Resources$NotFoundException` under a platform dialog theme, because the attribute points at a 9-patch/ripple drawable there — the same trap as the `TypedValue.data` one above, one layer deeper: the attribute is legitimate, its TYPE is not. Fall back to `?android:attr/colorBackground` for the background of a contrast ratio; a background that resolves to neither is `UNMEASURED` and must be reported as such — never substitute white and call the ratio measured.

- **`View.draw(Canvas)` does NOT apply the view's own alpha (2026-11-14, #162).** Alpha is applied by the PARENT in `drawChild` (`saveLayerAlpha`), so a root with `alpha = 0` still paints at full opacity when the test calls `root.draw(canvas)` directly — a render test then "sees" text the user never sees. The smoke test therefore draws the faded container's PARENT; the synthetic self-tests assert exactly this pair (alpha on the view vs alpha on the parent) plus height 0, a covering sibling and a healthy control.

- **The platform `textColor*` attributes are TRANSLUCENT and fail WCAG in light mode (2026-11-14, #161).** `Theme.Material.Light` ships `textColorTertiary` ≈ 2.5:1 on `#FAFAFA` and `textColorSecondary` at 4.54:1 — a borderline pass that drops below 4.5 on the app's own `#F0F0F3` (measured 4.00:1 for `#70777C`); disabled text is 26 % black = 1.88:1 on the "Forget" button. That is why the app theme now declares its own opaque palette instead of inheriting the platform's. Calibration for new colours: the maximum grey that still passes 4.5:1 on `#F0F0F3` is `#6D6D6D` — measure any "muted" tone, never eyeball it.

- **A queue figure must never be rendered as a duration (#116, found 2026-11-12).** The stage line showed `pendingAudioSeconds()` — every committed-but-untranscribed audio second, INCLUDING the in-flight request. Measured over 317 clean sessions: displayed median 10.7 s / p90 22.0 s against a real stop→raw wait of median 1.65 s (RTF 0.07). A user sees "22 s → STT", waits 1.7 s, and reports a timing bug. Rule: the stage line shows the audio length of the fragment CURRENTLY in flight (emitted at request start); the backlog stays in the logs. Second, smaller trap in the same lines: the old guard `if (pendingSeconds > 0)` meant no event was emitted at 0, so the last figure lingered until the next stage overwrote it.

- **`requestHideSelf(0)` does NOT change the default IME — only `switchInputMethod(target)` does (#155).** Hiding the input view just closes the bar for now; the *default* keyboard is untouched, so the next field focus opens Polished again. Symptom: "I tapped X, and the next text field shows Polished again." Any "hand the field back to the typing keyboard" action must call `switchInputMethod(resolveKeyKeyboardTarget(selfId))` (and fall back to `openKeyboardSettings()` when no target exists or the switch did not take effect — `currentDefaultImeId()` is still `selfId` right after, because the change notification is async). `requestHideSelf(0)` is not used any more in the post-send path either (#174: Send keeps the voice keyboard like a typing keyboard); it survives only where an explicit "close the bar for now" is wanted.

- `android.R.drawable.ic_media_stop` does not exist in the Android SDK. Create a custom `VectorDrawable` for a stop/square icon.
- OxygenOS (OnePlus) overrides system drawable icons — `ic_menu_preferences` renders as a wrench, not a gear. Use custom drawables for guaranteed appearance across OEMs.
- `ArrayAdapter.clear()` and `addAll()` modify the internal `mOriginalValues` list (not `mObjects`) when `mOriginalValues` is non-null — which it always is after constructor initialization. A custom `Filter.publishResults()` that calls `clear()` + `addAll()` never updates the displayed data (`mObjects`), only corrupts `mOriginalValues`. Use `BaseAdapter` + `Filterable` with a directly owned display list. Never use `clear()`/`addAll()` in a custom ArrayAdapter filter.
- `ArrayAdapter.setNotifyOnChange(false)` is never reset to `true` after a filter's `publishResults` returns, leaving the adapter in a permanently non-notifying state that causes crashes on subsequent text input.
- AutoCompleteTextView dropdown items (`DropDownListView`) cannot contain focusable child views (e.g. `ImageButton` with `focusable="true"`). The ListView refuses to deliver `onItemClick` for any row that has a focusable child — even tapping the non-focusable text area of that row fails. Keep dropdown items as plain `TextView` or use views with `focusable="false"`. For secondary actions, move controls outside the dropdown (separate dialog, long-press, etc.).
- To use an `AutoCompleteTextView` as a tap-to-open selector (HTML `<select>` behavior): set `inputType="none"`, `threshold = Int.MAX_VALUE`, `cursorVisible="false"`, and — critically — `setOnClickListener { showDropDown() }`. Without the click→`showDropDown()` hook the dropdown never opens, because `inputType="none"` blocks typing and the popup is otherwise only triggered by text input reaching `threshold`. Also set `focusable="false"` + `focusableInTouchMode="false"` (keep `clickable="true"`): `EditText` defaults to focusable-in-touch-mode, so the **first** tap on an unfocused field is consumed to gain focus and does not fire `onClick` — the symptom is needing 2–3 taps to open the dropdown until the field has been used once. Re-create the adapter (`setAdapter(ArrayAdapter(...))`) rather than `clear()`/`addAll()` when the option list can change between foregroundings (e.g. via `onResume` after a Settings detour), so the displayed list is always authoritative regardless of ArrayAdapter internal `mOriginalValues` state. Guard programmatic `checkBox.isChecked =` restores with a silence-flag so the `OnClickListener`/`OnCheckedChangeListener` doesn't write the just-read value back to prefs.
- Android VectorDrawable (`<vector>`) does not support SVG `<filter>`, `<pattern>`, `<clipPath>`, or `<feDropShadow>` elements. Gradients, drop shadows, mesh patterns, and glow effects from a high-quality SVG cannot be directly ported — render to PNG instead.
- Plain `inputType="text"` on ID-like AutoCompleteTextViews (model IDs) lets the IME autocorrect/suggestions replace typed fragments with learned words — on-device this manifested as "typing a period inserts the last active model" (#50). Use `text|textNoSuggestions` + `importantForAutofill="no"` for such fields.
- `AutoCompleteTextView` with `threshold=1`: with non-empty text, focusing re-filters to matches of the current text (often 1 item); with empty text, `enoughToFilter()` is false → no dropdown at all. To show the full list on tap you must explicitly reset the adapter state (`showAll()`) and call `showDropDown()` in a click listener — BUT the internal focus-triggered filter runs **async** and its `publishResults` lands *after* the click handler, shrinking the list back (#50 round 2). Robust fix: return the full list from `performFiltering` when the constraint exactly matches a list entry — every trigger path then yields "all".
- Model-ID `AutoCompleteTextView` + period key: typing `.` is just the contains-filter matching every dotted ID (Qwen, llama-3.3, …) — on-device it looks like "the period inserts a recent input" because the active model is usually among the matches. Not a bug; documented to prevent re-diagnosis (#50 round 3).
- Provider/target-language dropdowns are `focusable=false` (`inputType=none`) — selecting an item never moves focus away from other fields, so focus-loss validation doesn't fire. Dropdown item-click listeners must explicitly re-run model validation (`SettingsActivity.setupDropdowns`, #50 round 3).
- `InputMethodService` cannot request runtime permissions directly (it's a service, no activity result API). Use a transparent trampoline `Activity` (`MicrophonePermissionActivity`) that calls `registerForActivityResult(RequestPermission())` and `finish()`es; the IME launches it with `FLAG_ACTIVITY_NEW_TASK` when `RECORD_AUDIO` is missing.
- An auxiliary voice IME subtype needs `android:imeSubtypeMode="voice"` + `android:isAuxiliary="true"` in `res/xml/voice_method.xml`. `android:overridesIme` is **not a public attribute** — AAPT rejects it; omit it. A `<subtype>` requires a unique `android:subtypeId` (a hex int **within signed-int range**, i.e. < `0x80000000`; larger values fail resource linking).
- Recording audio inside an active `InputMethodService` on Android 14+ requires a foreground service of type `microphone`: declare `android:foregroundServiceType="microphone"` on the IME `<service>` and call `ServiceCompat.startForeground(this, id, n, ServiceInfo.FOREGROUND_SERVICE_TYPE_MICROPHONE)` only **after** `RECORD_AUDIO` is granted (else `startForeground` throws). `ServiceCompat` handles the version-branching of the 3-arg `startForeground`.
- IME input-view layouts must avoid `MaterialButton`/Material-components views: the `InputMethodService` inflates with the service context, whose theme is not a Material3 theme → `MaterialButton` crashes at inflation. Use plain `android.widget.Button` (e.g. `@android:style/Widget.DeviceDefault.Button.Borderless`) + `TextView`.
- `commitText` from a coroutine callback must hop to the Main thread; the `VoiceSessionController` already delivers events on Main (Handler(mainLooper)), so the IME's `handleEvent` can call `currentInputConnection.commitText(...)` directly.
- **IME layout: `?attr/` (Material theme attrs) crash in the service context** — concrete instance: `<ImageButton android:background="?attr/selectableItemBackgroundBorderless">` → `InflateException` → `UnsupportedOperationException: Failed to resolve attribute at index 13` → crash loop (system restarts the IME → `onCreateInputView` crashes again → the `UncaughtExceptionHandler` fires `CrashDialogActivity` repeatedly). Fix: `android:background="@null"` or `?android:attr/selectableItemBackgroundBorderless` (PLATFORM attr, resolves in any context). This generalizes the prior pitfall: **every** background/tint/style attribute in an IME layout must be a platform attr (`?android:attr/...`), a resource (`@color/...`, `@drawable/...`), or `@null` — never a bare `?attr/` (Material/AppCompat). Test IME layouts by switching the active keyboard to Polished; a crash here loops and the only recovery is `adb uninstall`.
- **~~HeliBoard's mic button uses the system `voice_recognition_service` (bound `RecognitionService`), NOT the auxiliary voice IME~~ — OBSOLETE (verified on-device 2026-09-07, OnePlus 7T/Oplus):** current HeliBoard versions detect Polished's auxiliary voice IME directly — the mic button works out of the box with no bound `RecognitionService` and no `voice_recognition_service` write. The old claim (from an older-HeliBoard-era XDA whisperIME tutorial) was the entire premise of issue #62, which was closed not-planned. Would-have-been details if ever revisited: on stock Oplus the setting is unwritable anyway (app-side `WRITE_SECURE_SETTINGS` is signature|privileged; shell-side blocked, see the Oplus pitfall above), so a bound service is only deployable on S5-style custom ROMs. Design direction for a hypothetical re-add: independent capture flow sharing only `VoiceSessionController.prepareAudioFile()` (#60), FGS type `microphone`, trampoline permission, `RecognitionService.Callback` constraints (results on `onStopListening`'s thread / Main, `readyForSpeech(Bundle.EMPTY)`, `ArrayList<String>` for `RESULTS_RECOGNITION`).
- **`Spinner` dropdown items are unreadable in the IME service context** — platform `simple_spinner_item`/`simple_spinner_dropdown_item` inherit text color from the theme; the service context's default theme yields dark-gray text on a dark popup → near-zero contrast on Oplus. Fix: custom item layouts with **explicit hardcoded colors** (`ime_spinner_item.xml`: black text, transparent bg; `ime_spinner_dropdown_item.xml`: **white row background, black text**) — never rely on theme-derived colors in an IME. (Issue #44.)
- **An auxiliary-only IME (`android:isAuxiliary="true"` on the only `<subtype>` in `voice_method.xml`) cannot be set as the primary keyboard — the nav-bar keyboard switcher isn't rendered when only one non-auxiliary IME is enabled.** Fix (#46, shipped `f4ebca4`): add a second, **non-auxiliary** keyboard `<subtype>` (`isAuxiliary` omitted → default false; `imeSubtypeMode="keyboard"`; unique `subtypeId` hex < `0x80000000`) to the same `<input-method>` so Polished appears as a selectable primary keyboard AND the switcher renders for `Gboard + Polished`. `isAuxiliary` is per-subtype, so one IME exposes both: the non-aux keyboard subtype (primary, selectable) + the existing aux voice subtype (HeliBoard/Fossify integration). Confirmed on-device: switcher renders for `Gboard + Polished` with the #46 build. **Do NOT add `android:isAsciiCapable="true"` to the non-aux keyboard subtype** — see the next pitfall for why.
- **AOSP "Manage Keyboards" greyed-out rule (`InputMethodSettingValuesWrapper.isAlwaysCheckedIme()`, `frameworks/base/packages/SettingsLib/.../InputMethodSettingValuesWrapper.java` + `InputMethodAndSubtypeUtil.isValidNonAuxAsciiCapableIme()`): an IME's enable/disable toggle is greyed out (disabled) only when EITHER (A) it's the sole enabled IME left (`getEnabledInputMethodList().size() <= 1`, no `isSystem`/ASCII requirement), OR (B) it's the last enabled **system** (platform-signed) + non-auxiliary + ASCII-capable **keyboard** IME. The current/default IME (`Settings.Secure.DEFAULT_INPUT_METHOD`) is **never** consulted in the greyed-out decision — AOSP explicitly allows disabling the current default (`InputMethodAndSubtypeUtilCompat` save path clears `DEFAULT_INPUT_METHOD` and lets `InputMethodManagerService` pick a new one). `isAuxiliary` only *excludes* an IME from counting toward `enabledValidNonAuxAsciiCapableImeCount` (via `if (imi.isAuxiliaryIme()) return false`); it never locks an IME. `isAsciiCapable()` returns true only if the subtype declares `android:isAsciiCapable="true"` — default is false. LineageOS's copy is byte-identical to AOSP `main`; no OEM override was needed to explain the observed behavior.**
- **`isAsciiCapable` decision (#46): deliberately NOT set on Polished's non-aux keyboard subtype.** On-device 7-row evidence table (Oplus/OnePlus, all consistent with AOSP — no OEM override):

  | State | Greyed-out | AOSP prediction | Match |
  |---|---|---|---|
  | Gboard alone | Gboard | (A) sole IME → greyed | ✓ |
  | Polished alone | Polished | (A) sole IME → greyed | ✓ |
  | HeliBoard alone | HeliBoard | (A) sole IME → greyed | ✓ |
  | OpenBoard alone | OpenBoard | (A) sole IME → greyed | ✓ |
  | Gboard + Polished | Gboard | count=1 (Polished not ASCII-capable) → Gboard last system non-aux ASCII kb → greyed | ✓ |
  | HeliBoard + Polished | neither | count=1 (Polished not ASCII-capable) → HeliBoard non-system → not greyed | ✓ |
  | Gboard + HeliBoard + Polished | none | count=2 (Gboard+HeliBoard) → none is last system | ✓ |

  Adding `isAsciiCapable="true"` would make Polished count → `Gboard + Polished` count=2 → Gboard not greyed → both toggleable → user could disable Gboard and strand Polished as the sole IME. Since Polished has **no QWERTY layout** (it's a voice bar), stranding would leave the user with no way to type normal text. Leaving `isAsciiCapable` unset keeps AOSP's user-protection (Gboard stays greyed in `Gboard + Polished`, preventing the strand). The switcher still renders regardless (confirmed on-device) — `isAsciiCapable` affects only the greyed-out toggle rule, not switcher rendering. Trade-off accepted: Polished is "second-class" in `Gboard + Polished` (Gboard protected) vs `Gboard + HeliBoard` (neither protected, since HeliBoard declares `isAsciiCapable` and is a real typing keyboard).- **Under `Theme.DeviceDefault` (non-Material), bare `?attr/` (AppCompat/Material theme attrs) and `?attr/textAppearance*` do NOT resolve** — AAPT/aapt2 accepts them at build time (no error), but inflation throws `UnsupportedOperationException: Failed to resolve attribute at index N` at runtime. This generalizes PITFALL #83 (IME service context) to *any* non-Material theme: use `?android:attr/...` (platform), `@android:style/...`, `@color/...`/`@drawable/...`, or explicit `android:textSize`/`android:textColor` literals. Concrete instance in #45: `item_manage_language.xml` had `?attr/selectableItemBackground` and `?attr/textAppearanceBody1` → both replaced with `?android:attr/selectableItemBackground` and `textSize=16sp`+`?android:attr/textColorPrimary`. The platform `?android:attr/textColorPrimary`/`secondary`/`tertiary` ARE DayNight-aware (the `values-night` resource set overrides them), so explicit `textSize` + platform text-color attrs preserves dark mode without Material.
- **A bare `AutoCompleteTextView` with `inputType="none"` (HTML `<select>` behavior) needs a manual `setOnClickListener { showDropDown() }` + `threshold = Int.MAX_VALUE`** — Material's `ExposedDropdownMenu` end-icon provides the tap→open hook automatically; a plain `AutoCompleteTextView` does not, and `inputType=none` blocks typing so the dropdown is otherwise unreachable. Already documented for the IME (PITFALL #37) but it also applies to the post-#45 Settings provider/target-language dropdowns, which lost Material's exposed-dropdown wrapper. Keep `focusable="false"`+`cursorVisible="false"`+`clickable="true"` so the first tap opens the dropdown (not just focuses the field).
- Dropdown rows MAY contain a **clickable but non-focusable** child (`focusable="false"` + `focusableInTouchMode="false"`): `AbsListView` only blocks `onItemClick` for rows with `hasFocusable()` descendants. Long-press is NOT an alternative: `AutoCompleteTextView` has no `setOnItemLongClickListener`, and a long-clickable row consumes touches. **Refined on-device (#48/#53→#59): this is NOT sufficient in practice** — see next pitfall.
- **`switchToPreviousInputMethod()`/`switchInputMethod()` DESTROY the current IME service** — `onDestroy()` runs on switch. Per-IME-service state (session controller, PCM buffer) dies with it unless held app-scoped: `VoiceSessionController` must come from `PolishedRecognitionApp`, and IME `onDestroy` must `detach()` (not `cancel()`) a PAUSED session to preserve the dictation across keyboard switches. (#65.)
- **Launch the target activity BEFORE `switchInputMethod()` when both happen in one IME handler** — the switch destroys the IME service, so any `startActivity`/work after it races the unbind; dispatch the activity intent first (imperceptible ordering difference). IME-launched `SettingsActivity` needs `FLAG_ACTIVITY_NEW_TASK or FLAG_ACTIVITY_CLEAR_TOP` — plain NEW_TASK reattaches to the app task whose root may be a stale launcher-Settings instance, and Back would land inside that stale instance instead of the dictation app (#59 class, #72).
- **The mic-coupled RMS pulse chain was removed in #87** — the noise-gate and PCM sign-correction pitfalls below moved to HISTORY.md. Re-read them before re-adding any audio-coupled UI.
- **`maxOf(x, NaN) = NaN` and `coerceIn` passes NaN through** — a single NaN poisons downstream math silently (no crash). When mixing animated values with sensor/audio data, filter non-finite inputs at the boundary.
- **The IME row pulse is only *driven* during RECORDING** — `ValueAnimator.cancel()` leaves the last animated `breathAlpha` applied, so pausing during the dim phase would freeze the IME near-invisible. Rule: alpha outside RECORDING must be pinned explicitly (`PulseAlphaPolicy.target` returns `1f` for IDLE/PAUSED/PROCESSING); never `applyAlpha()` from stale pulse state. (#77, still in force after the #87 sine rewrite removed the second `voiceAlpha` layer.)
- **`AutoCompleteTextView` popup row-clicks are unreliable on Oplus when a row contains a VISIBLE clickable child** — rows WITHOUT the child (built-ins, trash `GONE`) selected fine; rows WITH the visible trash ImageButton (customs) swallowed label taps entirely: no selection, dropdown never closed (user-verified twice; synthetic adb taps gave inconsistent wrong-row results). Pitfall #113's "clickable non-focusable child works" does NOT hold for the popup path on this ROM. Robust fix (shipped ac75231): give the row label an **explicit click listener** that commits selection (`settings.targetLanguage`/`setText(item, false)`) + `dismissDropDown()` — same pattern as the manage-languages dialog; never rely on the ListView's internal item-click machinery for custom-row dropdowns. (#48/#53, fixed #59.)
- **`SettingsHintActivity` (or any IME-launched dialog activity) with `FLAG_ACTIVITY_NEW_TASK` attaches to the app's existing task** — if the launcher activity (`SettingsActivity`) is still alive in that task, finishing the dialog drags it to front, dumping the user INTO Settings mid-dictation (the exact circular trap the hint warns about). Fix (shipped ac75231): `android:taskAffinity=""` on the hint activity → its own task → OK returns to the previous app. (#59.)
- **IME bar bottom-row icons were hardcoded white** (`ic_close` stroke `#FFFFFF`, `ic_pause`/`ic_send` fill `#FFFFFF`) — invisible on the light-mode `recording_overlay` background. Fix (ac75231): tint at the USAGE site (`android:tint="@color/recording_icon_tint"` on the IME ImageButtons) — NOT in the drawables, which `VoiceRecognitionActivity` reuses on colored (red/blue) Material buttons where white is correct. Tint survives runtime `setImageResource` swaps (pause↔resume, mic↔send).
- **Root-view alpha pulse reads differently per theme**: `rootView.alpha` dims background + children uniformly, but a white overlay dimmed over the dark IME window (light mode) visibly pulses the "background" while a black overlay over dark (night) is invisible — only icons appear to pulse. If theme-consistent feedback is wanted, pulse the foreground rows, not the root. (ac75231.)
- **IME→IME switching needs `<queries>` package visibility on API 30+** — `InputMethodService.switchInputMethod(id)` throws `IllegalArgumentException` when the target IME is "filtered by the rules of package visibility", and IME-list queries come back empty. The fix is a manifest `<queries><intent><action android:name="android.view.InputMethod"/></intent></queries>` block (grants visibility to all packages declaring an InputMethod service). (#65.)
- **`InputMethodService.switchToPreviousInputMethod()` cannot be trusted as a switch-button decision point for a voice IME** — it resolves "last" from the `input_methods_subtype_history` secure setting (most-recent-first, enabled IMEs only) and IMMS rewrites that history with the CURRENT IME at the head after **every** settings touch (enable/disable any keyboard, even via adb). While we are the current IME, "last" therefore resolves to **ourselves**; IMMS then performs a self-targeted subtype switch (silently aborted — it logs `Illegal subtype state: old subtype = null` because our IME never sets a current subtype) and still returns **`true`** → any `on false` fallback is dead code. Resolve the target yourself from the history and use `switchInputMethod(id)` instead (`SwitchTargetPolicy`, #65).
- **`InputMethodManager.showInputMethodPicker()` is useless as fallback for an IME with no other keyboard enabled** — the picker lists *enabled* IMEs, so the fallback state shows a dialog with only Polished itself; in some call contexts the request is also silently dropped server-side (`canShowInputMethodPickerLocked`). On-device (S5/LineageOS 18.1): tapping the old picker fallback produced NOTHING visible — neither the dialog nor a log line. Use `Settings.ACTION_INPUT_METHOD_SETTINGS` instead (#65).
- **`Settings.Secure.getString` returns cached values with async invalidation** — an immediate read after a settings write (e.g. checking `default_input_method` right after `switchInputMethod()`) can still return the old value because the ContentObserver-based cache invalidation hasn't landed yet. For deterministic fresh reads, query the single-name URI directly: `contentResolver.query(Uri.withAppendedPath(Settings.Secure.CONTENT_URI, "<key>"), arrayOf(Settings.NameValueTable.VALUE), …)` (#65).
- **`Character.isWhitespace()` does NOT recognize NBSP (U+00A0)** — it covers ASCII whitespace + newlines/tabs but returns false for non-breaking spaces; `Character.isSpaceChar()` covers NBSP/space separators but NOT newline/tab. Whitespace detection at InputConnection boundaries must use the union `isWhitespace(c) || isSpaceChar(c)` (`InsertionSpacingPolicy`, #66) — otherwise text inserted before/after an NBSP gets an extra space.
- **Some apps return `null` from `getTextBeforeCursor`/`getTextAfterCursor`** (not only at field start) — a null neighbor is indistinguishable from "no characters here". Policy decision (#66): treat null as "no whitespace present" → the padding space is still added, so a missing separator can never corrupt word joins in the common case.
- **The IME row pulse (`breathAlpha`/`voiceAlpha`) is only *driven* during RECORDING** — `RmsChanged` is ignored outside RECORDING and `ValueAnimator.cancel()` leaves the last animated `breathAlpha` applied, so any `applyAlpha()` from `setFlashing(false)` froze the rows at the paused-moment value (floor 0.15 during the dwell → near-invisible IME in PAUSED). Rule: alpha outside RECORDING must be pinned explicitly (`PulseAlphaPolicy` returns `1f` for IDLE/PAUSED/PROCESSING); never `applyAlpha()` from stale pulse state. (#77.)
- **A VectorDrawable stroke that reaches the viewport edge is clipped by half (#95).** `ic_backspace`'s right edge sat at `x=24` in a 24-unit viewport; its 1.6 stroke extended to 24.8, so only 0.8 rendered and the right edge looked thinner than every other stroke. Rule: keep `content edge + strokeWidth/2` inside `[0, viewportWidth]` (same applies to the left tip at x=0). Fix: inset the path, or wrap in a `<group android:pivotX="12" android:pivotY="12" android:scaleX/Y="0.9333">` (compensate the stroke with `strokeWidth = 1.6 / 0.9333` to keep the on-screen width).
- **A non-selected IME cannot switch itself back — no public API, ever** (#72 context, evaluated + rejected 2026-10-09). `switchInputMethod()` / `InputMethodManager.setInputMethod()` / `switchToLastInputMethod()` all require the token of the CURRENTLY bound IME; once Polished has switched to the key keyboard for the settings detour, it is unbound and neither the dead IME instance nor `SettingsActivity` can restore it programmatically. Remaining routes: `WRITE_SECURE_SETTINGS` + writing `default_input_method` (blocked on Oplus adb anyway, hostile for users) and `showInputMethodPicker()` from a foreground activity (works, but the owner rejected it — an extra click). Accepted flow: return to the target app with HeliBoard active, its mic key re-invokes Polished via the auxiliary voice subtype and the paused session auto-resumes (#83).
- **Der sichtbare Rebind-Koller war die Atem-Animation, nicht der Zustand (#118 Phase C, 2026-11-23).** Pro Zyklus malte `applyUiState` neu, `startMicForeground` betrat erneut `startForeground`, `updateNotification` postete erneut und `startBreathing()` cancel+erzeugte den `ValueAnimator` — die Atem-Phase sprang auf jedem Zyklus zurück. Fix: identische Arbeit überspringen (`service/RebindChurn` + per-Instanz-Flags), NIE eine echte Änderung unterdrücken; die `churn=render:… fgs:… notify:… breath:…`-Zeile in `ime-lifecycle.log` zeigt pro Intervall, was wirklich passierte.
- **The IME has exactly ONE editor-insertion site — `PolishedVoiceInputIME.handleEvent` → `Event.Completed` → `handleCompletedSuccess()` → `insertResultText()` → `commitWithSpacing()`; there is no streaming/incremental insertion (#118, 2026-10-10; the seam names are #174).** Every editor commit is a terminal `Completed` event (cancels go to the clipboard, as does the crash dialog). So "partial text got inserted" can only mean an `Event.Completed` carried a partial string — currently reachable via raw-mode rescue (`runTranscription` delivers the partial join when a fragment finally fails and `rawMode` is on) or via `pendingResult` re-delivery on `attach()` after a rotation. Diagnose insertion complaints from this single site. **Phase A (2026-10-10, `99b2e46`) made this observable:** `Event.Completed` now carries `redelivered` (came from the `pendingResult` hold) and `partial` (`failedIndex`/`chunkCount`), and every insertion logs to the `insertion.json` stream (`surface` ime|service, `reason` LIVE|REDELIVERED|RAW_RESCUE_PARTIAL, `length`, origin-vs-current `FieldId`, `hasConnection`) — correlate with `ime-lifecycle.log` by timestamp. Note `restore()` emits only `StateChanged(PAUSED)`, never `Completed`, so a perceived "text appeared without a send" must still resolve to a send/stop.
- **An IME switch destroys the IME instance — the post-success teardown runs `cancel()` with state IDLE (#138, 2026-10-14; the switch itself is gone since #174).** #133's `switchInputMethod` after a successful send was an IME *replacement*: the old `PolishedVoiceInputIME` got `onDestroy()`, whose IDLE branch calls `controller.cancel()` as pure teardown. #174 removed that switch (Send keeps the voice keyboard), so this chain no longer starts on a send — but the guard is still needed for every other teardown (rotation, process death, a later X). Consequences: (a) any resource a successful session leaves behind MUST be consumed before `deliver()` — the transcriber's success cache (kept for the retry-after-failure re-drain) otherwise masquerades as undelivered paid-for work in that later cancel and emitted the #113 salvage (toast + clipboard) AFTER the text was already inserted; (b) `cancel()`'s salvage must key on an actual session existing (`state != IDLE`), not on "the cache has content" — a cache is not a session. Diagnose any "action fires after a successful send" report along the Completed → destroy → onDestroy(IDLE) → cancel chain, and check `ime-lifecycle.log` for the destroy right after the insertion.
- **`applyUiState()` re-enables every quick setting — a per-target disable must live INSIDE `setQuickSettingsEnabled` (2026-11-19, #168).** `PolishedVoiceInputIME.refreshQuickSettings()` disables the LLM toggle for our own app, but `onStartInputView` calls `applyUiState()` right after, whose IDLE/RECORDING branches call `setQuickSettingsEnabled(true)` — the toggle came back enabled and the UI test caught it while the unit test on the policy passed. Any state that must survive a session-state change belongs in `setQuickSettingsEnabled`, not only in the refresh path.

- **`AutoCompleteTextView` is NOT an `AdapterView` (2026-11-19, #171).** It delegates `setOnItemClickListener` to an internal popup, so a test cannot drive an item click through the listener (`ClassCastException: AutoCompleteTextView cannot be cast to AdapterView`). Expose the selection handler as an `internal fun onLanguageSelected(index)` and call that from both the listener and the test.
