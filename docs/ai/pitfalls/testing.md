# Pitfalls — Testing and the Harness

Moved out of `PITFALLS.md` in #206; entries are verbatim. New pitfalls in this area are appended here.

- **`exit value 2` im Test-Fork ist der Crash-Handler der App, nicht der Heap (2026-11-24, #198).** `PolishedRecognitionApp.onCreate` installiert einen JVM-globalen `setDefaultUncaughtExceptionHandler`, der mit `Process.killProcess` + `System.exit(2)` endet; Robolectric instanziiert die Application im Test-JVM. Also tötet **ein** unbehandeltes Throwable auf irgendeinem Hintergrund-Thread den ganzen Fork: partielle Ergebnis-XMLs, kein `<failure>`, kein `hs_err`, kein OOM-Text — und genau das war über Wochen als „Heap zu klein" (#86/#131) fehldiagnostiziert (der Kommentar in `build.gradle.kts` ist seit #198 korrigiert). Wer das Symptom sieht: **erst den Throwable sichtbar machen** (`CaptureThreadGuard`, `Log.e` im Handler), dann die Ursache im Thread fixen. Wer in einem Robolectric-Test einen Live-Take startet, stellt den Handler um (`@Before`/`@After`) — sonst reißt ein Test die ganze Suite mit.
- **Ein Robolectric-Test darf nicht darauf bauen, dass der Shadow-`AudioRecord` schon Bytes geschrieben hat (2026-11-24, #199).** Ob eine Session den Live-Pfad (`finishTranscription`) oder den Batch-Pfad (`transcribe`) nimmt, entscheidet `FragmentTranscriber.drain().chunkCount > 0` — also ob tatsächlich Audio da war. Unter Last ist der Spool bei `stopAndTranscribe()` noch leer und der Test kippt (in `VoiceSessionControllerTest` genau einmal passiert, 3/3 alleine grün, im CI-förmigen `test + lintDebug` rot). Deterministisch wird es nur über einen **restaurierten Snapshot** (dessen `prepareTailSync()` synchron kodiert), nicht über einen laufenden Take.
- **A `@Part` with a Kotlin default value is NOT `any()` in MockK (2026-11-20, #184).** `every { api.call(any(), any(), any(), any(), any()) }` on a method whose last two params default to null records the invocation as `…, null, null` — a production call that actually passes values then matches nothing and fails with "no answer found". When a mocked signature grows defaulted params, update every stubbing site to the full arity (`any()` for each), not just the failing test.

- **On `claw` `/tmp` is a 1.9-GB tmpfs, and a Robolectric test that starts a REAL `AudioRecord` fills it in about a second (2026-11-20, #177/#178).** Capture writes to `cacheDir` (Robolectric maps it under `/tmp/robolectric-*`) at CPU speed, with no codec or real-time throttle — the spool grows from megabytes to gigabytes while the test is still asserting. The first visible symptom is `java.io.IOException: Disk quota exceeded`, after which Gradle reports `Process 'Gradle Test Executor N' finished with non-zero exit value 2` although every result XML in `*/build/test-results/` shows 0 failures. Do NOT start live recordings in tests (Robolectric records nothing anyway, #116); if it happens: `./gradlew --stop`, remove `/tmp/robolectric-*`, retry.
- **Under Gradle 9.5 + configuration cache, `:app:cleanTest` reports `UP-TO-DATE` and `--rerun` does nothing (2026-11-20, #178).** Forcing a real test run by asking Gradle nicely does not work — delete the test result directories (`app/build/test-results`, `app/build/reports/tests`, plus the `:core`/`:analyzer` equivalents) and pass `--no-build-cache`. **Dieselbe Falle bei Lint (2026-11-24, #200 gemessen):** `:app:lintDebug` kann `lintReportDebug UP-TO-DATE` melden, während der Report auf Platte Stunden älter ist als die Quelländerung — ein „No issues found" von gestern ist kein Gate für heute. Vor dem Vertrauen die mtime von `app/build/reports/lint-results-debug.txt` gegen die letzte Quelländerung prüfen; im Zweifel `rm -rf app/build/reports/lint-results-debug.* app/build/intermediates/lint*` und mit `--no-build-cache` neu laufen lassen (`lintAnalyzeDebug` UND `lintReportDebug` müssen `executed` sein).
- **Known flakes that redden a full gate without a code cause (2026-11-20, #178) — beide aufgelöst am 2026-11-24.** `VoiceSessionControllerTest > flush in PROCESSING is a no-op` wurde in #199 über einen restaurierten Snapshot deterministisch, `SettingsStoreTest > evidenceRetentionSeconds defaults to 0` (`expected: 0 but was : 2592000`) in #200 über den reinen Lese-Getter (siehe den #200-Eintrag oben). Die Lehre bleibt: einen Flake NICHT als „bekannt" abhaken und die Assertion nicht umschreiben — den **schreibenden Thread** finden. Ein Executor-Abbruch mit null `<failure>`-Einträgen gehört zum selben Verdacht (#198).

- **Robolectric's default density is mdpi (1.0) (2026-11-14, #162).** A 1080×2400 window is a 1080-dp "tablet", not a phone: 14-sp text renders 14 px tall, boxes are far wider than on the device, and nothing about the layout matches the opo's 450 dpi. Deterministic ≠ device-shaped — pin the qualifier (`@Config(qualifiers = "w411dp-h891dp-xxhdpi")`) if a comparison to a real screenshot is intended; the render test deliberately relies on determinism only.

- **A rare, unidentified unit-test flake (2026-10-11 … 2026-10-13, six recorded occurrences — mitigated by #131, `717c194`, but NOT extinct).** Executor exit 2 mid-suite (312/462, 318/465, 321/~481 on 2026-10-13 22:57) with 0 recorded failures, single re-run always green; same region as #86. Root cause hypothesis confirmed as A fix, not THE fix: the test heap (1536m since #86) no longer fit the grown suite, and #131's test-only `maxHeapSize = "2048m"` reduced the frequency but the flake recurred twice on 2026-10-13 alone (the #133 push and the deployment-docs push — the latter with evidence finally captured: partial `test-results/` with 321 tests/0 failures/0 errors, daemon log `~/.gradle/daemon/9.5.1/daemon-1427136.out.log` shows `Process 'Gradle Test Executor N' finished with non-zero exit value 2`, NO hs_err file). Full occurrence history in HISTORY.md. If it recurs: capture `app/build/test-results/` + executor stderr BEFORE any re-run — and suspect a leaked recorder thread first (PITFALLS entry below), not the heap. [ACTIVE watch until two clean weeks]
- **Robolectric records NOTHING — compress-on controller tests via `recordAndStop()` exercise the LEGACY path, not the fragment path (#116).** Under Robolectric the mic capture yields an empty buffer, so `prepareTailSync` commits zero fragments and the controller falls through to `prepareAudioFiles`/`pipeline.transcribe` (this silently shaped the #115 tests too). Fragment-path controller tests MUST use the hand-crafted snapshot/restore pattern (`session.pcm` + `session.meta` with a `sessionId`, then `restore()` → `stopAndTranscribe()`) — and must NOT call `start()` on a restored (PAUSED) session: that re-begins recording and resets the restored buffer. Capture events after a restore via `attach { }`, not `start { }`.
- **Events delivered after a `withContext(Dispatchers.IO)` resumption arrive via a main-looper post — a Robolectric test must pump the looper before reading them (#116).** When the live fragment worker processes on an IO thread, `emit()` posts the `Completed` event to the main Handler; the test thread's poll of `state` works, but the events list stays empty until `shadowOf(Looper.getMainLooper()).idle()` runs. (Tests whose whole flow stays on the test thread see the events directly — which is why the older tests never hit this.)
- **Robolectric tests must wait on EVENTS, not state fields, when the producer posts from an IO thread (#117 flake).** The failure branch posts `Completed` to the main looper AFTER publishing PAUSED; a test that polls the state field and pumps once races the post (the suppressed `UnExecutedRunnablesException` in the flake's failure report is the smoking gun). The test helpers now have `awaitEvents(events, predicate)` (pumps inside the poll loop). `awaitState` alone stays safe for the SUCCESS branch (which posts `Completed` BEFORE the IDLE state write — observing IDLE implies the post is queued) and for file assertions under the snapshot-before-publish ordering.
- **MockK 1.14 matcher/answer API traps (#117).** (a) `slot` is a FUNCTION (`slot<T>()`), not a type — a function signature returning `slot<Foo>` does not compile; the type is `io.mockk.CapturingSlot<T>`. (b) `capture(slot)` requires a NON-nullable slot type and does not match null; for nullable args use `captureNullable(slot)` with a **nullable slot type** (`slot<RequestBody?>()`) — the reverse combination fails with a confusing "None of the following candidates is applicable". (c) `nthArg` does not exist on the answer scope in 1.14 — use `invocation.args[i]` (an `Any?` list, cast yourself). (d) Reified MockK helpers constrain `T : Any` — nullable type arguments are rejected at compile time.
- **Truth's byte-array subjects have no `hasSize`/`containsOnly` (#117).** `assertThat(ByteArray)` yields `PrimitiveByteArraySubject` — use `.size` / `isEqualTo(ByteArray(...))` / elementwise loops; and `isEqualTo` on a `List<ByteArray>` compares array IDENTITY, not content — compare elementwise.
- **Hand-crafted fragment manifests in tests MUST carry `end` offsets (#117).** A manifest entry without `end` (pre-#117 shape) is treated as legacy and the whole prefix is discarded + re-encoded — a reuse-assertion test silently becomes a re-encode test. New shape: `{"name":...,"bytes":N,"end":<pcmOffset>}`.
- **FragmentPreparer tests must inject `searchBytes = 0` for legacy fixed-cut behavior (#117).** With the default 2-s search window the encoder WAITS when the nominal 7-s boundary is reached without silence found (never splits a word mid-window) — sync-test expectations like "tail = remainder after the last full fragment" only hold at `searchBytes = 0`; silence tests craft zero-filled PCM regions and small windows.
- **Transcriber tests must derive the fragment index from the runner's `chunk` arg (`thirdArg<Int>() - 1`), NOT the uploaded file's name (#117 round 2).** With a pre-roll the upload is composed into `upload_<i>.<ext>` — a name-based derivation breaks. Related: composed uploads are DELETED in `finally`, so a captured `File` reference read after the call throws `FileNotFoundException` — capture `readBytes()` at call time.
- `captureNullable<ChatRequest>()` requires an explicit type parameter in the slot approach. Prefer `slot<ChatRequest>()` for capture semantics.
- Local Gradle test-worker JVMs can die with a bare `java.io.EOFException` in `testDebugUnitTest` under memory pressure (20/30 GB in use here); there is no assertion failure in the XML reports — it is a forked-JVM crash, not a test failure. The same crash also surfaces as `Process 'Gradle Test Executor N' finished with non-zero exit value 2` with zero recorded failures. Before blaming pressure, rule out a leaked live recorder (next pitfall) — the #87 session's exit-2s looked environmental but were the leaked-recorder thread. Genuine pressure flakes clear on plain retry; a leak fails deterministically at the same class. Re-run to confirm; do not chase a phantom test bug. The pre-push hook runs the same suite — a hook failure from a flake just needs a re-push, never `--no-verify`. **Amended 2026-11-23 (#192):** the archived recorder is faster than "a leak" suggests — the shadow `AudioRecord` returns a full buffer with no I/O wait, so a take that stays live for ONE SECOND fills the sandbox temp filesystem (`IOException: Disk quota exceeded` on the recorder AND the fragment worker, from `/tmp/robolectric-<class>-<test>/…/cache`). Two consequences: never let a test keep a take live across an `idleFor`/sleep (start → assert → `cancel()` within a few statements), and produce a PAUSED take through `controller.restore()` over a hand-crafted `session.{pcm,meta}` instead of a real pause. A resume re-opens that capture, so IME-level resume ROWS are pinned through the decision (`PolishedVoiceInputIME.lastEntryAction`, also in the `onStartInputView` trace) rather than by executing `controller.resume()`.
- **Robolectric cannot run `MediaCodec`/`MediaMuxer`** — any encoder/transcoder test must mock the `AudioTranscoder` interface and verify the fallback wiring; real-encode verification is on-device only (`installRelease`). `VoiceSessionController` takes `AudioTranscoder` + `SettingsStore` as constructor params precisely for this.
- **Robolectric's `AudioRecord` shadow fills the recorder buffer in a tight loop — and its `read()` never blocks.** The shadow's default source returns the full requested size instantly, so a live capture thread appends at full CPU speed. Consequences: (1) any wall-clock wait between `start()` and `pause()`/`stop()` inflates the buffer to gigabytes and OOMs the test JVM (first seen as `OutOfMemoryError` in `ByteArrayOutputStream.ensureCapacity` via `restorePcm`); (2) worse, a test that ENDS with the recorder still RECORDING leaks the spinning thread into every subsequent test — 2026-09-19 (#87 follow-up `3eed55d`): `start resets a preserved paused session` left the session RECORDING with no cleanup, filling GBs across the rest of the suite and killing the worker with exit value 2 at the pipeline→service boundary (misdiagnosed as pressure first — even a 3g worker OOMed). Rule: snapshot/restore tests must hand-craft small `session.{pcm,meta}` files instead of round-tripping a real `pause()`; never `Thread.sleep` with a live controller under Robolectric; and EVERY test that starts recording must pause/stop/cancel before its final assert. (The flaky forked-JVM `EOFException` under memory pressure in the older pitfall is a different, environmental failure — re-run to confirm.)
- **Gradle's 512m default Test-worker heap kills the full suite with exit value 2 once the suite outgrows it** — symptom (2026-09-19, #86: 244 tests): `testDebugUnitTest` fails with `Process 'Gradle Test Executor N' finished with non-zero exit value 2`, every package passes in isolation (`--tests` per package green), pristine-smaller suite green, and no assertion/heapdump in the XMLs — the death lands deterministically at the same package boundary (here: pipeline→service). Diagnose by bisection: drop one test class via `--tests` filters; prove heap by bumping workers with an init script (`tasks.withType(Test) { maxHeapSize }`) WITHOUT touching the repo. Fix: `maxHeapSize = "1536m"` in `app/build.gradle.kts` `testOptions.unitTests.all` (test-only, release artifacts unaffected). Do NOT chase it as a code bug and do NOT "fix" it by deleting tests.
- **Exit value 2 can recur WITH the 1536m heap fix in place — but check for a leaked recorder thread before blaming pressure.** The #87 session (2026-09-19, 235 tests, 24/30 GB used) looked exactly like pressure (executor died repeatedly, passed on retry/--info, per-package runs green, even a 3g worker OOMed with a 1.18 GB dump) and was first misdiagnosed as environmental. Real cause: `start resets a preserved paused session` ended with the recorder still RECORDING — under Robolectric the shadow `read()` returns a full buffer instantly without blocking, so the leaked thread spins at full speed appending to the buffer for the rest of the suite (GBs; crash always lands at the pipeline→service boundary). The #87 sine rewrite amplified it by removing the per-iteration sqrt/emit throttle from the capture loop. Distinguish leak from pressure: run the suspect class whole vs in quarters at 512m (quarters green + whole red = accumulation), or watch for a test that starts recording without a matching pause/stop/cancel. Fix is cleanup in the test, NOT bigger limits. Do NOT raise `maxHeapSize` for this signature and do NOT "fix" it by deleting tests. NOTE (2026-10-14, #143 pre-push): the executor also died with exit 2 while the tests were up-to-date and immediately green on retry (known environmental flake shape, no leak) — re-run before diagnosing.
- **Robolectric tests must never produce bulk audio through the live recorder** — the multi-chunk controller test (`VoiceSessionControllerTest`, #115) hand-crafts `session.{pcm,meta}` and uses `restore()` so the PCM size is deterministic; also snapshot the chunk files INSIDE the pipeline mock (`firstArg<List<File>>().map { name to readBytes() }`) because the controller deletes them right after the pipeline returns.
- **`VoiceSessionControllerTest`'s legacy-path tests can flake when Robolectric's capture is momentarily non-empty (#118 session, 2026-10-10).** `stopAndTranscribe passes the caller package to the pipeline` assumes the legacy path (`pipeline.transcribe`), but the live fragment path runs whenever the captured buffer is non-empty — observed once as a 2-byte capture → one fragment → `finishTranscription` called instead, so `coVerify { pipeline.transcribe(...) }` failed (right after 8 green suite runs; not reproducible in isolation, not caused by the change that triggered it). Same load-sensitive class family as the #117 flake (see HISTORY). Re-run rather than chase it; a deterministic fix would hand-craft an empty snapshot instead of relying on the Robolectric capture.
- **Robolectric-Prefs leaken NICHT über Testmethoden — die Datei ist pro Testmethode frisch (#200-Korrektur der #142-Lehre).** `AndroidTestEnvironment.setUpApplicationState` legt je Testmethode ein neues `TempDirectory` an (`Files.createTempDirectory("robolectric-<pkg>")`), und `ShadowSharedPreferences` ist in Robolectric 4.14.1 eine **leere** Klasse — es läuft die echte `SharedPreferencesImpl`. Ein verspäteter `apply()` aus Test A schreibt damit in eine bereits gelöschte Datei und ist für Test B unsichtbar; gelesen wird aus der In-Memory-Map, die `clear().commit()` auf DERSELBEN Instanz leert. Ein „geleakter Default" ist deshalb immer ein **gleichzeitiger Schreiber** (2026-11-24 gemessen: der App-Start-Thread, PITFALLS #200), niemals ein alter Wert auf Platte. `clearPrefs()` bleibt als Hygiene sinnvoll, heilt aber nur, was VOR dem Clear geschrieben wurde — es kann einen Schreiber danach nicht aufhalten.
- **JUnit XML failure attribution can nest the `<failure>` element under the WRONG testcase (#142 lesson).** The `<failure>` element's position within `TEST-*.xml` does not reliably match the test that failed; the enclosing `<testcase name="...">` found by a naive regex may be a NEIGHBOR. Diagnose from the STACK's class + line numbers (and the message's own wording) instead of the surrounding element — a wrong attribution costs a full mis-debugging round.
- **Robolectric + `setText` on a model dropdown clears its `error`, and `SharedPreferences` state is only observable after the activity's own writes (#150 test lessons).** Two traps hit while writing `SettingsActivityTest`: (a) `EditText.error` is cleared by the very next `setText`/`TextWatcher`, so an assertion on `.error` must be the LAST step after the save tap, never inside the configuration lambda; (b) a test helper must not assume "abort ⇒ prefs untouched" — `saveAndClose()` writes the provider before the wrap/fragment checks, so compare only the key under test, not `prefs().all`. The original wording blamed "#142 retention getters materialise keys on read" — since #200 the retention getter is a pure read, but the rule stands: a getter may migrate once, and never trust the whole map.
- **Relaxed MockK mocks do NOT store property values (2026-11-19, #168).** A `mockk(relaxed = true)` of `TranscriptionPipeline` answers every property getter with the relaxed default and swallows setters, so `pipeline.forceRawMode = true` followed by `pipeline.forceRawMode` reads `false` — a "the controller set the flag" test fails although the production code is right. Observe the SETTER instead: `every { pipeline.prop = any() } answers { recorded += arg<Boolean>(0) }` (note `arg<Boolean>(0)`, plain `arg(0)` cannot infer the type).
