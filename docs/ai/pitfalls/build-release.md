# Pitfalls — Build, Release and Tooling

Moved out of `PITFALLS.md` in #206; entries are verbatim. New pitfalls in this area are appended here.

- **Ein vergifteter Build-Cache-Eintrag meldet „resource mipmap/ic_launcher not found", obwohl die Datei da ist (2026-11-25, Build).** `installRelease` brach in `:app:processReleaseResources` mit `AAPT: error: resource mipmap/ic_launcher … not found` ab, `app/src/main/res/mipmap-anydpi/ic_launcher.xml` lag aber unverändert und getrackt im Baum. Die Ursache war **nicht** das Manifest und **nicht** die Quelldatei: `:app:mergeReleaseResources` kam `FROM-CACHE` und restaurierte ein merged-res-Verzeichnis **ohne** die mipmap-`*.flat`-Dateien (der lokale Eintrag in `~/.gradle/caches/build-cache-1` war inkonsistent). Diagnose in zwei Schritten: (a) `rm -rf app/build/intermediates/merged_res/release && ./gradlew :app:mergeReleaseResources --no-build-cache` — erscheint die mipmap dann im Output, ist der Cache schuld; (b) `./gradlew --stop && rm -rf ~/.gradle/caches/build-cache-1` und neu bauen. Merke: „resource not found" bei einer nachweislich vorhandenen Ressource heißt erst Cache/Merge-Output prüfen, nicht Manifest oder Datei „reparieren" — und `mipmap-anydpi` (ohne `-v26`) ist für das adaptive Icon in Ordnung, solange `minSdk >= 26` ist.

- **OBSOLET seit #193 (2026-11-24): es gibt keine `app/lint-baseline.xml` mehr.** Die drei folgenden Baseline-Einträge beschreiben, wie sich eine Baseline verhält — nur noch relevant, falls je wieder eine eingeführt wird (was `XmlColorPolicyTest` Regel 6 jetzt verhindert). Der Lint-Lauf ist total: `warningsAsErrors = true`, null Befunde, Ausnahmen nur als `@Suppress`/kommentierte `lint.xml`-Ignores (#193).

- **`lintVitalRelease` runs FATAL checks only — a global lint baseline therefore always looks "stale" there (2026-11-22, #187).** `assembleRelease`/`installRelease` print "N errors/warnings were listed in the baseline file … but not found in the project" plus "The baseline was created using a different target/variant than it was checked against. Creation variant: lint, Current variant: lintVitalRelease". That is NOT rot: `app/lint-baseline.xml` is written by the global `lint` task (`variant="all"`, every check) while the vital run executes only fatal-severity checks, so it matches the one fatal entry and reports the rest as unfound. AGP 9.1.1 has no per-variant baseline (`com.android.build.api.variant` exposes no baseline property), so the mismatch cannot be configured away. ACCEPTED (owner decision): keep `checkReleaseBuilds` at its default for the fatal gate; do not "refresh" the baseline to chase this message and do not read it as a signal. The real staleness signal is `LintBaselineFixed` on `lintDebug`.

- **A literal `%` in `strings.xml` is a format specifier — twice is a build warning, and a wrong conversion is a fatal lint error (2026-11-22, #187).** `slice_seconds_hint`/`search_percent_hint` contain "10–60 %" style text, so AAPT printed "Multiple substitutions specified in non-positional format … Did you mean to add the formatted=\"false\" attribute?" on every `merge*Resources` (debug and release), and lint reported the fatal `StringFormatInvalid` on the same string. A single `%` does not warn (AAPT only rejects two or more), which is why the neighbouring `search_percent` looked fine. Fix: `formatted="false"` on any string with literal percent signs that is never formatted; never add it to a string that takes arguments.

- **A baselined "newer version available" notice stops matching on its own (2026-11-22, #187).** `NewerVersionAvailable`/`GradleDependency`/`AndroidGradlePluginVersion` compare against the live repositories and put the found version IN THE MESSAGE ("9.9.1", "4.17"). When upstream publishes 9.9.2/4.18.1 the old entry matches nothing, lint reports it as fixed (`LintBaselineFixed`) and raises the same notice again as a new finding — every upstream release costs a baseline edit. Keep these IDs out of the baseline (`severity="ignore"` in `app/lint.xml`); the same hazard applies to any check whose message embeds environment state.

- **`TextContrast` is NOT a lint check in lint 32.1.1 (AGP 9.1.1) — declaring it is inert config (2026-11-14, #163).** Verified by jar inspection and empirically: `<issue id="TextContrast" severity="error"/>` in `app/lint.xml` neither runs nor complains about being unknown, so a green `lintDebug` says nothing about contrast. The effective gate is `XmlColorPolicyTest` (no raw literals in `res/layout`+`res/xml`, no bare `?attr/`, `@color/` refs present in both modes, palette parity both ways, `recording_*` ≥ 4.5 per mode, baseline never holds a contrast issue). Do not treat the lint declaration as coverage, and do not "fix" a contrast regression by trusting it.

- **The build pins Java 21 via the Gradle toolchain — don't run the build on an unintended JDK (#107).** Gradle otherwise uses whatever JDK it runs on. If the test JVM is newer than the bundled MockK/ASM supports (JDK 25 → major version 69), the suite fails en masse with `java.lang.IllegalArgumentException: Unsupported class file major version 69` (143/292 failed on 2026-10-05) while being fully green on JDK 21. Fix (persisted, not per-agent): `app/build.gradle.kts` declares `java { toolchain { languageVersion = JavaLanguageVersion.of(21) } }`, so compile + test tasks use a JDK 21. Requirement: a JDK 21 must be **installed** (auto-detected) — Gradle does not download one. CI already uses Temurin 21.

- **The `pre-push` hook is NOT active in a fresh clone — activate it (#107).** Git only ships `pre-push.sample`; the repo's real hook lives at `scripts/pre-push` and must be linked: `ln -sf ../../scripts/pre-push .git/hooks/pre-push`. Until then a `git push` runs **no** tests, so a red state can reach `main`. Verify with `test -x .git/hooks/pre-push`. See `AGENTS.md → Git Hooks — REQUIRED`.

- **A commit message can auto-complete an issue — even when the sentence negates it (#82).** GitHub parses completion keywords (`close`/`closes`/`closed`, `fix`/`fixes`/`fixed`, `resolve`/`resolves`/`resolved`) next to an issue reference, and it ignores negation. A commit body line like “do not close #82 without OK” **closed #82 on push** (2026-10-03, immediately reopened). When a commit only *mentions* an issue that must stay open, keep those tokens away from the issue number (or paraphrase).

- Kotlin 1.9.x compiler cannot read Kotlin 2.1.x stdlib metadata. When test dependencies pull newer Kotlin stdlib transitively, upgrade the project Kotlin plugin to match.
- R8 full mode strips generic type information from the `Continuation<? super Response<T>>` parameter in Kotlin suspend functions within Retrofit interfaces. `HttpServiceMethod.parseAnnotations` casts to `ParameterizedType` and crashes with `ClassCastException: java.lang.Class cannot be cast to java.lang.reflect.ParameterizedType`. - AGP 8.2.2 bundles R8 that cannot parse Kotlin 2.1.x metadata. The R8 warning "An error occurred when parsing kotlin metadata" appears on every release build. Minimum AGP version for Kotlin 2.1 is 8.6, minimum R8 is 8.6.17. Upgrade AGP to 8.7+.
- R8 full mode inlines private methods and reorders instructions within `onCreate()`. `lateinit var` view fields initialized via `findViewById` in a separate `bindViews()` method may be accessed in `loadSettings()` BEFORE `bindViews()` assignments execute. Use `val by lazy { findViewById(...) }` instead of `lateinit var` + separate init method.
- `isShrinkResources = true` removes views from layouts in release builds even when the view is referenced in Java/Kotlin code via `findViewById`. Keep `isShrinkResources = false` unless resource keep rules are explicitly verified.
- A conditional `signingConfig` is required so local `installRelease`, CI, and F-Droid coexist. Define it in `app/build.gradle.kts` guarded by `if (file("release.keystore").exists())`, both when creating `signingConfigs.release` and when assigning `release.signingConfig`. The keystore is gitignored: present on the dev machine (→ signed `app-release.apk`, `installRelease` works) and in `build.yml`/`fdroid-apk.yml` via the `RELEASE_KEYSTORE` secret decode (→ signed `app-release.apk` too, since #82 `18bd2c3`); absent only in F-Droid's build env and `release.yml` (which signs the AAB via `-Pandroid.injected.signing.*`, orthogonal to build.gradle). An **unconditional** `signingConfigs` block breaks F-Droid because the referenced keystore file is missing in their container.
